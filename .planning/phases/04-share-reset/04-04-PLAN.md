<objective>
Close the loop between the board and the address bar, in both directions.

Four things already exist and are not built here: `App.serialize.scheduleUrlSync()` is already called
from `commit()` and from `undo()`, inside a `try` whose `finally` schedules the frame; `start()`
already reads the hash three times through `hasFlag`; `attempt(label, fn)` already exists as the
non-terminal wrapper; and `resetToDefaults` already commits structurally through the same funnel.
This plan fills the no-op the file has carried since day one and adds one read at boot.

**Three decisions this plan takes rather than inherits.** `04-CONTEXT.md` settled four questions and
none of them is one of these, so each is written into the file beside the code rather than left in a
planning document:

1. **`history.replaceState`, not `location.hash =`.** The only hash write in the artifact today
   (`:9388`) is a bail-out that clears the hash and reloads from a state where memory is untrustworthy
   — a different act. A mirror written through `location.hash =` pushes a history entry per debounced
   commit, so a student's Back button walks their whole edit history and the address bar starts
   behaving like a second undo stack, which is exactly what SHARE-05 says never to present. The Node
   stub grows a three-line `history.replaceState` that writes `location.hash`, so the gate can drive
   and read the mirror rather than asserting it by grep.
2. **The boot load creates no undo entry (D-20), and the mechanism is a second named writer in
   `[S03]`, not `restore()`.** `restore()` clears the stack and is `[S09]`-only by name in two
   banners; reaching for it here would make "after confirming, Ctrl+Z still brings the build back"
   impossible for paste as well as for reset. The new writer is guarded so it can run **once**, and
   only before any commit has happened — which is a boundary a student press can never reach.
3. **A refused paste returns a record; it does not throw.** Every other op in `[S05]` throws on a
   refusal and `App.boot.wrap` turns that into the styled panel. A bad paste is an expected outcome of
   a feature, not a defect, and SHARE-03 asks for a clear message rather than an error panel — so this
   op hands back the same four-token record `decode` produced and plan 04-07 writes the sentence.

Purpose: SHARE-05 end to end, and the one write path a pasted code will take in plan 04-07.
Output: a live mirror, a boot reader, two load ops and a guarded second writer.
</objective>
