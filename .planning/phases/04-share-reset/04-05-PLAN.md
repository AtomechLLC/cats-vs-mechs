<objective>
Build the surface, and build it so the code on it can never be stale.

`04-CONTEXT.md` D-21 settled that **share and load are one dialog with two panes**, matching
`#act-edit` rather than adding two roots. It did not settle the reset confirmation, and research is
explicit that a confirmation is not a pane of a share surface — it is a different act, with a
different opener, and Phase 5 will want it on the topbar beside share. **So this plan ships two
dialogs: one with two panes for share and load, and a small separate one for the confirmation.** The
arithmetic: the share surface is about fifteen shell ids and the confirmation about five, against 73
today.

The single highest-consequence failure this surface can have is a build code on screen that no longer
describes the board. `[S06.5]`'s own paragraph states the general rule — *a selection naming nothing
is a reason to repaint onto something live, never a reason to stop painting* — and the Phase 4
equivalent is sharper: **a code that no longer matches the board is a reason to produce a new one,
never a reason to leave the old one where a student will copy it.** That is what the fingerprint in
Task 2 exists for.

D-19 also lands here, and it must be recorded beside the code rather than only in a planning file.
Two ops in this repo **decline** a confirmation in writing, and the one time that policy met a
competing requirement the answer was a permanent line rather than a modal. Reset is different, and
the difference is measured: `resetToDefaults` adds exactly one undo entry and one Ctrl+Z restores the
build byte-for-byte, **but that entry falls off the thirty-deep stack after thirty further commits.**
Every other destructive action in this file stays recoverable for as long as the student keeps
working; reset is the only one whose escape hatch can age out from under them. That is what makes the
confirmation load-bearing rather than ceremonial, and it is the argument the file's own precedent
(`clampTokenName`, which opens *"the one technique in this phase with no precedent anywhere else in
the file"*) says to write down at length.

Purpose: the surface SHARE-01, SHARE-04 and SHARE-06 are operated through.
Output: two dialogs that arrive complete — markup, ids, stubs, harvest entries, styles — and a
repaint that keeps the code honest.

<the_two_decisions_this_plan_makes>
**1. Two dialogs, not one, and not three.** D-21 settled share and load into one dialog with two
panes. The reset confirmation is the third thing, and it gets its own root: it is a different act
with a different opener, it must read as unmistakably different from the non-destructive controls
(SHARE criterion 4 says so in as many words), and Phase 5 will want reset on the topbar beside share
rather than buried in a share surface. The cost is four or five shell ids and one more
`DIALOG_ROOTS` entry, both of which are arithmetic rather than judgement. D-21's own status note says
splitting is a cheap deviation if the panes fight; this is the adjacent call, made once, here.

**2. The code field is written even while it holds focus. The paste field never is.** These are
opposite answers to D-19 and the plan states both with their reasons. The paste field holds text a
student typed, so a repaint that overwrites it loses half-typed input — the rule `#tok-pick-name`
already carries. The code field holds text the artifact produced, and the failure mode is the reverse:
a student who focused the field to select it, then changed the board in another window, would copy a
code describing a board that no longer exists. So the code field is rewritten whenever the build
moves, **and the selection is re-applied afterwards** if it held one.
</the_two_decisions_this_plan_makes>
