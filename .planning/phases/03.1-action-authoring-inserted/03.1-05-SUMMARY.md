### No second `fire()` payload-key exception was needed

The plan asked this to be settled explicitly. `fire()`'s four keys — `side`, `unitId`, `delta`, `tokenId` — remain the file's **one** recorded exception to the attach-rather-than-edit banner, and this plan did not add a second.

It did not need one because every press inside the dialog is read by the dialog's **own** delegated listener, which calls `App.ops.dispatch` directly with a patch built field by field, exactly as `onPickerPress` already does for `setTokenStyle`. The three keys the action ops take — `side`, `actionId`, `name` — are assembled in `[S07.3]` from the pressed control and the dialog's own bookkeeping. `fire()` is never on the path.

Only the topbar button routes through `[S07.1]`, and it carries **no payload at all**: `openActionEditor` is a UI-only act that reads the dialog's dataset and nothing else. It must never grow a `data-side` — a hidden side on that button would be the topbar growing a control per faction, which is the thing the comment beside it says out loud it must not become.

## The decision this plan made, in writing

**One dialog with two panes, not two dialogs.** RESEARCH sketched the proposal as a second dialog (`#act-fire`). Three costs decided against it, and all three are written into the shell comment where the next reader will meet them:

1. Two dialogs are two topbar buttons, two `LATE_BINDERS` entries, two delegated roots and two fingerprints. One is one of each.
2. A modal opened from inside a modal stacks focus and close-request behaviour, and the Node stub has **no close-request behaviour at all** — so the stacking could never be exercised anywhere in this repo.
3. **The id budget, measured:** the picker cost 19 of the file's 37 shell ids. One dialog with two panes cost 20. Two dialogs would have landed this file near sixty.

Which pane is showing is `data-ed-pane` on the dialog node, owned by `[S06.5]`, and this plan never moves it.

**And the second topbar button is paid for.** Phase 2.1 collapsed a **row** of them into one, precisely because the row grew by one control per invention. The comment beside this one states the difference out loud: it is **one**, it is **permanent**, and it is **bounded** — every action a student ever authors is a row inside the surface it opens — and it **must not become one-per-anything**. A later phase wanting a control per action, per side or per round gets the answer D-05 already gave: put it in the surface, not on the bar.
