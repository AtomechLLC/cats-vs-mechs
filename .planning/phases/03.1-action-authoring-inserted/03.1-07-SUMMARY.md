## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] check 72c's edit-survives-a-repaint clause was vacuous**

- **Found during:** Task 2's probe Y.
- **Issue:** the row drove its outside repaint while the caret was still in the field. `showProposed` skips a focused field before it looks at the edited flag, so the row was testing the focus skip and reporting on the edit skip. With the edit guard removed entirely, 72c stayed green.

### Considered departures from the plan's own text, recorded rather than absorbed

**2. The driven acceptance run is in the interaction gate, not in `[S09.10]`.** Task 3 says "as one end-to-end sequence of rows in `[S09.10]`". That suite opens by stating that **every row in it is DOM-free on purpose**, so the terminal harness gets the whole of it rather than a skip row — and an acceptance run driven through the surface is the opposite of DOM-free. A row bracketed on `typeof document !== 'undefined'` there would not run in CI at all, which is `<prior_wave_notes>` item 7 exactly. So the DRIVEN half is check 73 in the gate, where it runs, and the BOUNDARY half is three DOM-free rows in `[S09.10]`, where it runs everywhere. Both halves exist; only their homes were swapped, and the reason is written at both sites.

**3. One control was added to the AUTHORING pane.** `#act-edit-prop-open` carries `data-ap="open"` and lives in the authoring pane's action row, because a pane with no way to reach it is a pane nothing can open. It is shell markup, not `[S07.3]`'s authoring half, and it carries `data-ap` rather than `data-act` so no handler above the proposal block can see it.

**4. `editorSig` was widened by TWO slots, not one.** The plan's own text implies the pane's bookkeeping; the rosters and the pool are the second slot and they are load-bearing for the same reason plan 03.1-06's vocabulary slot was: nothing on this surface drew a unit's name or a faction's action points until this pane existed.
