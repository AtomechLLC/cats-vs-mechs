# Phase 3.1: Action Authoring (INSERTED) — Research

**Researched:** 2026-08-28
**Domain:** Single-file vanilla-JS state modelling — extending a frozen data record into a
student-authored one, and deciding what a projection means when its inputs stop being fixed
**Confidence:** HIGH on everything measured in this repo. There is no browser here; every
layout, glyph and legibility claim is LOW and named as such at the end.

---

## Summary

Everything in this phase that looked structurally risky is cheap, and everything that looked
like a detail is the risk.

The **record shape is cheap.** `build[side].actions` is already in the build slice — actions are
nested inside each faction, not a top-level key — so D-09 costs nothing. Adding `cost` /
`req` / `xf` to an action, and adding those fields to the *shipped six inside `DEFAULTS`*, runs
the full 520-row in-file suite green with **zero assertion churn** (measured). Signed integers
survive `deepFreeze`, `thaw()` and the `allIntegers` walk. There is exactly one shipped row this
phase will redden, and the artifact predicted it in a comment: `refActions()` reads
`App.data.DEFAULTS[side].actions` while the projection reads `state.build[side].actions`, and a
tripwire row compares the two. **This phase is the day that read has to change on purpose.**

The **projection question (D-14) has a clean answer with the numbers to back it.** Generalise
`min(ap, active) * bestDamage` into `max over actions of min(floor(ap / apCost), active) * damage`,
where `damage` is the magnitude of an action's negative Health delta on the *target*, falling back
to `action.dmg` for a record with no transformations. This reproduces the shipped board **exactly**
(≈9 / ≈3), gets wider and less confident rather than more confident when a student authors a
big expensive hit (a 3-AP 12-damage action reads ≈3–9), and names — by action name, on screen —
anything it cannot model. A candidate implementation of it was written and run: **520 rows, 0
failed, shipped strip byte-identical, `.prj-ignore` count still 5, Layer A and Layer B clean.**

The **proposal should not live in state at all.** A new `ui` key reddens one row and, worse,
`setUi` refuses object values by contract. A fourth top-level slice reddens another. The
artifact's own precedent — stated twice in `[S06.2]` and `[S07.2]` — is that transient
"which surface is showing what" lives on the dialog node, and the picker's `<input>` is *static
markup specifically so it survives repaints*. A proposal is a form the student is editing before
submitting. Build it as one, confirm it through a single new op, one commit, one Ctrl+Z.

The **two real hazards are both about gates that cannot see this phase's work.** Layer C of the
PROJ-06 verdict gate harvests `#app`; `#tok-picker` is not a descendant of `#app`, and **96
rendered strings inside it are invisible to Layer C** (measured). Assembled-at-render proposal
copy — `'target ' + name + ' −' + n` — is exactly the case Layer B cannot read either. And the
stub DOM's `textContent` is non-recursive, which already makes one shipped row vacuous.

**Primary recommendation:** Extend the action record in `DEFAULTS` first (zero churn, all six
expressed in the new form), generalise `bestDamage` into an affordability-aware throughput with a
named admission line in the ignores box, build the proposal as a form on a new dialog rather than
as state, and extend Layer C to reach that dialog before writing a word of its copy.

## User Constraints (from CONTEXT.md)

### Locked Decisions — the developer's specification (D-01…D-05)

- **D-01:** An action carries a **cost**: a token type and an amount, **consumed** when the action
  fires. Default is one action point, matching what the shipped board already implies.
- **D-02:** An action carries **requirements**: token types and amounts that must be present for the
  action to be available, and that are **not** consumed. The example given was Health ≥ 2.
- **D-03:** An action carries **transformations**: each names **the caster or the target**, a token
  type, and the amount that token count changes by. An action may carry more than one.
- **D-04:** **The tool proposes; the student disposes.** *(Chosen explicitly over auto-apply and
  over check-only.)*
- **D-05:** The per-side **sequence** of actions is real and wanted, but lands in Phase 5 as
  FIGHT-12 — it is the fight loop, and this phase has no turn to hang it on.

### The line this phase walks (binding, quoted from CONTEXT.md)

> A tool that applied transformations would be resolving. **This tool does not apply them.** The
> student authors the rule; the tool reads that rule back and waits.
> - The tool **shows** what the student's own action says would happen.
> - The student **accepts it, edits any number in it, or overrides it entirely.**
> - **Nothing lands until they say so.**
> - The tool never decides *whether* an action happens, *who* it targets, whether a counter
>   applies, or what any of it is worth.
>
> **If an implementation ever finds itself deciding something, it has left the phase.**

PROJECT.md's Out of Scope list is **unchanged** by this phase and must not be quietly eroded.

### Claude's Discretion (D-06…D-16 — the planner may revisit any if research contradicts it)

- **D-06:** Extend the shipped record rather than replace it. `dmg` and `keywords` stay.
- **D-07:** A shipped action and a student's action are the same kind of thing. No second tier.
- **D-08:** Transformations are signed deltas, not verbs. "target Health −3", not "damage 3".
- **D-09:** Actions live in the `build` slice.
- **D-10:** Cap the authored actions per side. The number is a Phase 4 codec dial, set from
  measured encoding cost, not taste.
- **D-11:** An action naming a removed token type is refused by name, saying which action and

- **D-13:** The three-layer id gate applies to action ids too. Do not build a one-layer gate.
- **D-14:** `bestDamage` stops being well-defined and the planner must resolve it. *(Answered

- **D-15:** Whatever replaces it must keep PROJ-06. **Saying less is allowed; implying a verdict

- **D-16:** If the projection cannot model an authored action, it must say so plainly rather than

The proposal never enters `[S03]` before it is confirmed. That is the mechanical expression of
"nothing lands until they say so": there is no state in which a proposal exists and has not been
accepted, so nothing downstream — undo, the build code, the projection — can ever read one.

### Pattern 1: extend the record in `DEFAULTS`, not beside it

**What:** put `cost` / `req` / `xf` on all six shipped actions inside `App.data.DEFAULTS`.
**When:** first wave, before any surface exists.
**Why it is safe — measured:** the board-defaults suite projects actions through
`tuple(a) => [a.id, a.name, a.dmg, a.keywords]`, so extra fields are invisible to it; `refCard`
reads only `.name`, `.dmg`, `.keywords`; and the tripwire row compares `build.*.actions` against
`DEFAULTS.*.actions`, which move together.

```js
// Measured: all six rewritten in the new form -> 520 rows, 0 failed.
{ id: 'lasers', name: 'Lasers', dmg: 3, keywords: ['range'],
  cost: [{ tok: 'ap', n: 1 }], req: [], xf: [{ who: 'target', tok: 'hp', d: -3 }] }
```

**The trap inside this pattern:** *the whole suite staying green means the change is unproven.*
This is the WR-01/WR-02 shape exactly — a data change nothing asserts. The wave that adds these
fields must add rows asserting them, or the phase ships an unasserted data edit.

### Pattern 2: the token id is a VALUE, never a KEY

**What:** `cost`, `req` and `xf` are **arrays of records** carrying `tok` as a field —
`[{ tok: 'hp', n: 2 }]` — never objects keyed by token id — `{ hp: 2 }`.
**Why (measured):**

```
bag['__proto__'] = {...}     -> own keys []  |  prototype REPARENTED
bag['constructor']           -> resolves to a FUNCTION on the prototype
Object.create(null) through thaw() -> comes back a PLAIN object; the null prototype is GONE
[{tok:'__proto__',d:-3}]     -> survives the round trip; Object.prototype untouched
```

A keyed bag re-opens the exact CR-02 / Pitfall-2 surface `requireTokenId` exists to close, and
`Object.create(null)` cannot be the mitigation because `thaw()` is `JSON.parse(JSON.stringify(…))`
and the prototype does not survive it. An array of records has **no key position at all**, and
lookup is an `Array.find` over a `tok` field — the rule `styleFor`, `labelFor`, `effectRecord` and
`actionNameById` each state at length, for the reason they give.

### Pattern 3: the proposal is a form, not a slice

The picker's `#tok-pick-name` is **static markup**, and the shell comment says why in one
sentence: *"The dialog repaints on every frame while it is open, and a field rebuilt or
overwritten mid-typing loses the half-typed text; a node that is never rebuilt can simply be
skipped while it holds focus (D-19)."* A proposal is n such fields. Build them as static markup
in the new dialog, one per line the shipped board's richest action could produce, and show/hide
the surplus. Every ergonomic problem — Escape reverts, blur commits, a repaint must not overwrite
a focused field, focus restore through `data-k` — is already solved by `[S07]`'s numeric-field
contract and `showFieldValue`.

### Anti-patterns to avoid

- **A `ui.proposal` key.** Reddens `state contract :: the ui slice holds exactly its documented
  keys` (measured), and `setUi` throws `TypeError: ui.<k> must be a boolean, a whole number or a
  string` on an object value — its value allowlist is a contract, not an oversight.
- **A fourth top-level slice.** Reddens `state contract :: three slices` (measured).
- **A control on a reference card.** `refCard`'s comment says *"NO CONTROL OF ANY KIND"* and gate
  row 63b walks the built cards for a dispatched attribute. Measured: appending a `data-act`
  under a card puts `["act"]` in exactly the set 63b scans.
- **A second topbar button per surface.** 02.1 collapsed the topbar to one button precisely so it
  would not grow. A second one is defensible only because it is *one*, permanent, and bounded —
  it must not become one-per-anything.
- **A merge helper in the mutator.** `setTokenStyle` and `createTokenType` both write field by
  field with the same comment: a merge copies whatever keys the caller supplied, which is how a
  reserved key slips past an allowlist that only inspected the values. `cost` / `req` / `xf`
  entries must be built field by field too.
- **Storing the proposal's arithmetic.** A derived value in state is a second, mechanical reason
  for the projection to disagree with the board.
- **`eval` / `new Function` / a conditional rules language.** Banned by CLAUDE.md, and deferred by
  CONTEXT.md. An authored rule is a record the tool *reads*.

## D-14 — what happens to `bestDamage`. **Worked recommendation.**

### The problem, stated in the shipped numbers

`bestDamage(faction)` is `max(action.dmg)` — one scalar — and the whole strip rests on it:

```
factionDps  = min(faction.ap, activeUnits) * bestDamage(faction)
turnsToWipe = { hit: bestDamage, perTurn: factionDps,
                fast: ceil(ehp / perTurn), slow: ceil(soak / perTurn) }
soakTotal   = Σ over units of ceil(unitEhp(u) / hit) * hit
```

Shipped board, measured:

| | ap | units | eHP | best `dmg` | perTurn | soak | reads |
|---|---|---|---|---|---|---|---|
| Cats → Mechs | 3 | 9 | 27 | 1 (Slash) | 3 | 27 | **≈9 turns** |
| Mechs → Cats | 3 | 3 | 27 | 3 (Lasers) | 9 | 27 | **≈3 turns** |

`bestDamage` also has a **second, non-obvious consumer**: `amountFor(state,'dmg',side)` at
`[S06.1]` draws the *Damage token row on each faction head* from it. Changing it changes the
board, not only the strip. Any plan must account for both.

### The recommendation

Generalise in three named pure functions, all in `[S02]`:

```js
var HEALTH_KEY = 'hp';   // one of the five that CANNOT be removed (02.1 D-15), so it is always there.
                         // Bind to the KEY, never the name: a student renaming Health to Vigor
                         // changes `name` and nothing else.

function actionApCost(a) {            // null == this action has no throughput denominator
  if (!a.cost) { return 1; }          // a record with no cost is the shipped default, one point
  if (a.cost.length !== 1) { return null; }
  var c = a.cost[0];
  if (c.tok !== 'ap' || !Number.isInteger(c.n) || c.n < 1) { return null; }
  return c.n;
}

function actionDamage(a) {            // per-USE damage
  if (!a.xf) { return a.dmg; }        // the shipped six, unchanged, if left in the old form
  var d = 0;
  a.xf.forEach(function (x) {
    if (x.who === 'target' && x.tok === HEALTH_KEY && x.d < 0) { d -= x.d; }
  });
  return d;
}

function bestPair(faction, activeUnits) {
  var active = (activeUnits === undefined) ? faction.units.length : activeUnits;
  var hit = 0, per = 0;
  faction.actions.forEach(function (a) {
    var c = actionApCost(a);
    if (c === null) { return; }                       // not modelled — see unmodelled() below
    var uses = Math.min(Math.floor(faction.ap / c), active);
    var d = actionDamage(a);
    if (uses * d > per) { per = uses * d; hit = d; }
  });
  return { hit: hit, perTurn: per };
}
```

`bestDamage(faction, activeUnits)` returns `bestPair(...).hit`; `factionDps` returns
`bestPair(...).perTurn`. Both keep their existing arity — `activeUnits` was already optional and
already forwarded by `turnsToWipe` for Phase 5.

**Why this shape and not "damage per action point":** a *rate* is fractional. `soakTotal` divides
by `hit` and `ceil`s per unit, and `workLines` prints `soak` and `perTurn` on the page. A
fractional hit reaches a projector as `27.5 soaked ÷ 4.5 per turn`, which breaks D-06's
whole-numbers rule in `[S06.3]`. `min(floor(ap / cost), active)` is the same idea kept integral:
*how many times can this side afford this action this turn, times what one of them does.*

**Why `hp` only and not `hp + shield`:** measured both. A Cats action stripping 2 Shield from a
Mech reads **≈5 turns** under `hp+shield` and **≈9 turns, "Not shown in these figures: Rend"**
under `hp`-only. `hp`-only is recommended, for three reasons: it reproduces the shipped six's
`dmg` semantics exactly (Lasers 3 damage == target Health −3); `soakTotal`'s per-unit ceiling is a
statement about a *health* pool being ground down, and ceiling a shield-strip against
`maxHp + shield` is wrong twice over; and a shield strip is bounded (a Mech has 3) while the model
assumes an unbounded repeat, so counting it would *overstate* — the one direction PROJ-06 forbids.
Under `hp`-only the shield action is not dropped, it is **named**. That is D-16 satisfied.

### The admission (D-16) — a conditional line, **not** a sixth noun

```js
function actionModelled(a) {
  if (!a.cost && !a.req && !a.xf) { return true; }   // a bare shipped record: "Effects" covers it
  if (actionApCost(a) === null) { return false; }    // cost is not in action points
  var only = true;
  (a.xf || []).forEach(function (x) {
    if (!(x.who === 'target' && x.tok === HEALTH_KEY && x.d < 0)) { only = false; }
  });
  return only;                                       // a heal, a caster delta, a student token: not modelled
}
function unmodelled(faction) {
  return faction.actions.filter(function (a) { return !actionModelled(a); })
                        .map(function (a) { return a.name; });
}
```

Rendered as one `<p class="prj-note">` built once inside `projIgnores()`, carried `hidden` while
the list is empty — **the exact idiom the soak line already uses** in `projPanel`, and for the
same stated reason ("a line that exists is a line the sync pass writes in one branch"):

> `Not shown in these figures: Groom, Sacrifice.`

**Do not add a sixth noun to `PRJ_IGNORES`.** `[S09.8]` asserts `it names exactly five things` and
`[C11]`'s CSS comment says the separators are drawn *so the list holds exactly five nouns in the
document*. A conditional line changes neither, and it is stronger D-16 compliance: it names the
specific actions rather than gesturing at a category.

**Precision that matters:** `actionModelled` returns `true` for a record with **no** cost/req/xf.
Without that arm, Hairball, Screech, Fly and Recharge — four of the six shipped actions — would
all be named on a board where the student has authored nothing, which is noise, and is already
covered by the permanent noun *Effects*. Corollary for the wave that rewrites `DEFAULTS`:
**give Hairball / Screech / Fly `xf: []`, and do not give Recharge a `caster shield +1`.** Its
`shield` keyword already carries the meaning and the table adjudicates it. Writing that gain into
`DEFAULTS` would put "Recharge" in the admission on the shipped board.

**Rules the planner must carry into it, each already established elsewhere in the file:**

1. `sync()` must **never** write a focused field (D-19). The dialog repaints on every frame while

2. Signature-keyed repaint, like `pickerSig`. And learn 02.1's lesson: **fingerprint everything

3. Confirm reads the field values, converts string→number **at that one call site** (`[S05]`'s

4. One op ⇒ one `commit` ⇒ one snapshot ⇒ **one Ctrl+Z**. This is `removeTokenType`'s stated

5. Guards outside the commit, so a refusal leaves no phantom undo step. The single documented

## Referential integrity (D-11, D-12, ACT-07)

### The check — cost, measured

One pure read, in `[S05]` beside `dropTally`, exported for the page:

```js
function actionsNaming(build, tokenId) {          // -> [{ side, id, name }]
  var out = [];
  ['cats','mechs'].forEach(function (side) {
    build[side].actions.forEach(function (a) {
      var names = false;
      (a.cost || []).forEach(function (c) { if (c.tok === tokenId) { names = true; } });
      (a.req  || []).forEach(function (c) { if (c.tok === tokenId) { names = true; } });
      (a.xf   || []).forEach(function (x) { if (x.tok === tokenId) { names = true; } });
      if (names) { out.push({ side: side, id: a.id, name: a.name }); }
    });
  });
  return out;
}
```

| Actions on the board | Full scan |
|---|---|
| 18 (6 shipped + 6 authored per side) | **0.75 µs** |
| 30 (6 + 12 per side) | **1.12 µs** |
| 54 (6 + 24 per side) | **2.04 µs** |

Against a frame budget of 16 ms this is free at every plausible cap. **It can run on every frame**
— which is what makes the recommendation below possible.

### D-12 — recommend a permanent line, not a modal

02.1's D-17 chose no confirmation on removal, and its reasoning was *"a modal would cost an
instructor a click mid-demo to guard against something undo already covers."* D-12 says something
is referenced now. Both can be true at once:

> **Put a line beside the picker's Remove button: `Poison is named by 2 actions.`**

Recomputed from state on every repaint, like `setEnabled('tok-pick-remove', …)` already is — the
picker's own comment says *"Both are re-decided from state on every repaint rather than toggled by
whoever last pressed something, so an undo moves them too."* This tells the student what will break
**before it happens** (D-12's literal requirement), costs no click, adds no dialog, and leaves
removal as one undoable commit. A `<dialog>` confirmation is the named alternative if the developer
wants a harder stop; it is strictly more expensive and strictly less visible.

### D-11 / ACT-07 — refuse by name, at fire time

`removeTokenType` deletes the type and drops its tallies in one mutator, but **it must not rewrite
actions**. A rewritten action is a silently changed rule, which is worse than a refused one.
Instead, `applyProposal` (and the editor's own preview) refuses:

> `Pounce names Poison, which is no longer a token type on this board. Nothing has changed.`

Written in the message style `requireTokenId` / `tallyType` / `removeTokenType` already use: the
refusal names *which action* and *which token*, and reads the **live record's name** so a student
who renamed Health to Vigor is told about Vigor. That is `removeTokenType`'s own stated technique.
Guard runs **outside** the commit.

### D-13 — the id gate for action ids, all three layers

The three layers, proven in 02.1 by peeling them one at a time (removing any single one left the
whole suite green):

1. `RESERVED_KEYS` named refusal — **fires first**, so a student who reaches `__proto__` reads
   what actually happened rather than "that is not an action on this board".
2. A shape pattern — recommend `ACTION_ID_PATTERN = /^x[0-9]{1,2}$/` built from a single
   `ACTION_ID_DIGITS` source, with a capturing sibling `ACTION_ID_CAPTURE`, exactly as
   `TOKEN_ID_DIGITS` / `TOKEN_ID_PATTERN` / `TOKEN_ID_CAPTURE` are. The width is written **once**;
   02.1's comment records that a second hand-written copy is how a widened cap produces colliding
   ids silently.
3. A `hasOwnProperty` existence check **inside the mutator**, on the detached copy.

Two details carried over verbatim:
- The id comes from a **sequence**, never derived from the name the student typed.
- The prefix must **not** be numeric-leading. 02.1's comment: `Object.keys` puts integer-like keys
  first, so an id such as `12` reshuffles the vocabulary and a positional Phase 4 codec then
  encodes the reshuffled version. Actions are an **array**, so the ordering argument is weaker —
  but the reserved-name argument is identical and the prefix costs one character.
- Do not reuse `t` or the ids of the shipped six (`slash`, `hairball`, `screech`, `fly`, `lasers`,
  `recharge`). Add a `requireNewActionId` mirroring `requireNewTokenId`.

## Common Pitfalls

### Pitfall 1: Layer C cannot see a dialog — **and this phase's copy lives in one**

**Measured:** the picker renders **96** strings; Layer C's harvest of `#app` reads **131** before
the picker is painted and **131** after. `#tok-picker` is not a descendant of `#app`.

Layer A reads the whole document, so *static* dialog markup is covered. Layer B reads string
literals, so a whole-string literal is covered. **What is covered by neither is assembled copy** —
`'target ' + labelFor(state, tok) + ' \u2212' + n` — which is precisely the shape every proposal
line takes. The gate's own closing note already lists this as limitation 5.

**Fix in this phase, before writing the copy:** extend Layer C's harvest to the new dialog with its
own floor. **And note the cost:** the picker's list rows write `labelFor(...)` into
`.pk-sw-label` with **no `data-lbl`**, so an extended harvest that includes the picker would redden
on a student who names a type `Winner`. Either extend the `[data-lbl]` / `[data-albl]` exemption to
every node whose text comes from `labelFor`, or scope the extension to the new dialog only.

### Pitfall 2: the whole suite stays green for a data-only change

**Measured:** adding `cost`/`req`/`xf` to all six shipped actions inside `DEFAULTS` runs
**520/0**. Nothing asserts the new fields, so nothing can notice them being wrong. This is
WR-01/WR-02's shape — *a check written against source spelling cannot see behaviour expressed
through a helper*, generalised to *a check that projects four fields cannot see a fifth*. Every
wave that adds a field must add the row that would go red without it.

### Pitfall 3: the stub's `textContent` is not recursive — a shipped row is already vacuous

**Measured:** `strip.children.length === 3`, a leaf reads `"Cats"`, and
`strip.textContent === ""`. Planting the literal word `Infinity` on a leaf leaves
`String(strip.textContent).indexOf('Infinity') === -1`. So the in-file row

> *"neither of the two things a raw division would have put on a projector appears anywhere in the strip"*

**cannot fail under Node.** It is meaningful in a real browser only. Any new probe that reasons
over a subtree's text must walk it explicitly.

### Pitfall 4: the selector engine is narrower than it looks

Measured against the real stub, from `#strip`:

| Selector | Result |
|---|---|
| `.prj-panel` | matched 2 |
| `[data-prj]`, `[data-prj="turns"]` | matched 8 / 2 |
| `section.prj-panel` | matched 2 |
| `p` | matched 1 |
| `#strip .prj-turns` (descendant) | **matched 0** |
| `[hidden]` (non-`data-` attribute) | **matched 0** |
| `.prj-panel > h3` (child combinator) | **matched 0** |

Write every new probe selector as a class or a `[data-*]`. A descendant or attribute selector
returns an empty list and the row passes on nothing.

### Pitfall 5: `NaN` launders through `thaw()` into `null`, and the integer walk accepts `null`

**Measured:** `JSON.parse(JSON.stringify({ n: NaN })).n === null`, and `[S09.3]`'s walk returns
`true` for `null`. A `NaN` delta that reaches state survives one commit as `NaN`, then becomes
`null` on the next unrelated commit, and the walk never notices. `requireDelta` and `int()` are the
only defence, and they only fire at the op boundary — so **every** number entering `cost` / `req` /
`xf` must pass through one of them. Related: `{ cost: undefined }` loses the key entirely through
`thaw()`, so an "absent" field and a "present but undefined" field are the same thing one commit
later; do not build logic that distinguishes them.

### Pitfall 6: a class-substring walk double-counts

While probing, `className.indexOf('ref-card') !== -1` reported **6** cards in a 3-card column,
because `ref-card-head` starts with `ref-card`. The probe was wrong, not the artifact. Any new
walk over `.act-*` classes has the same hazard by construction.

### Pitfall 7: `deepFreeze` and `Object.freeze` fail *silently* outside strict mode

A write to a frozen nested field threw nothing in a sloppy-mode probe and threw
`TypeError: Cannot assign to read only property 'd'` in a strict one. Every probe asserting the
freeze must be in strict mode, and must include the negative control (the same write on an unfrozen
copy must **not** throw) or it proves nothing.

### Pitfall 8: the naming trap now has five new ways to fire

`operating`, `iterating`, `enumerating`, `separating`, `decorating` all carry `rating`, and all
five are natural verbs for a phase about iterating transformations and separating cost from
requirement. **Describe, never quote.** The trap has fired seven times in this project, twice via
a comment quoting removed code.

### Pitfall 9: `bestDamage` has a second consumer on the board, not only in the strip

`amountFor(state, 'dmg', side)` draws each faction head's **Damage token row** from it. Changing
`bestDamage` changes the board. Measured: the recommended generalisation leaves it at 1 / 3 on the
shipped board, so nothing moves — but a plan that changed the semantics further would move the
red diamonds and nothing in `[S06.1]` would say why.

### Pitfall 10: `build[side]`'s key set is asserted nowhere

`Object.keys(build)` is pinned by four rows; `Object.keys(build[side])` by none. Measured:
`s.build.cats.proposal = {…}` reddens **nothing**. Convenient this phase, dangerous next one.
Recommend adding the row.

## Security Domain

The artifact has no network, no auth, no session and no storage that anything depends on. Most
ASVS categories are vacuous here; the one that is not is the one this project has already had to
close twice.

| ASVS category | Applies | Standard control in this file |
|---|---|---|
| V2 Authentication | no | — |
| V3 Session management | no | — |
| V4 Access control | no | — |
| **V5 Input validation** | **yes** | `int()` / `requireDelta()` / `requireSide()` / `requireTokenId()` / `requireTokenName()` — type test **before** any arithmetic, allowlist on the KEY as well as the value. |
| V6 Cryptography | no | — |

| Threat pattern | STRIDE | Mitigation, already in the file |
|---|---|---|
| Prototype pollution via a caller-supplied **key** (`tokens['__proto__'] = …` reparents; `var r = tokens[id]; r.name = x` writes onto `Object.prototype`) | Tampering | The three-layer id gate. **Extend it to action ids (D-13). Do not build a one-layer version — 02.1 measured that removing any single layer left the whole suite green.** |

| A student string reaching a markup sink | Injection | `createElement` + `textContent` only; the dev gate's `FORBIDDEN` scan enforces it document-wide. |
| **A student "rule" reaching an evaluator** | Code execution | **`eval` and `new Function` are banned. The authored rule must stay a data record the tool reads — this is the phase's defining constraint, not a nicety.** A conditional-transformation language is deferred for exactly this reason. |
| A pasted build code arriving from another student (Phase 4) | Tampering | Every lookup is an `Array.find` over a record's own `id`, or a `hasOwnProperty`-guarded read — never a bare index. **Pattern 2 above (`tok` as a value, not a key) is what keeps this true for `cost` / `req` / `xf`.** |

## Open Questions

### OQ-1 — **What does "confirm" actually write, when there is no fight?** *(blocking; put to the developer)*

**What we know, measured:**
- There is **no start-fight affordance anywhere on the page.** `startFight` / `endFight` exist as
  ops and in `dispatch`, but no `data-act` in the static markup and no `setData({act:…})` call
  anywhere renders a control for either. Grep of every rendered act found:
  `addUnit, ap, maxHp, removeUnit, selectTokenType, setTokenStyle, shield, tally`. A student
  **cannot** start a fight until Phase 5 ships FIGHT-01.
- `[S05]` reserves fight semantics to Phase 5 in writing, three separate times: action-point
  spending and damage application are "DELIBERATELY ABSENT, do not helpfully add them here";
  `setUnitHp`'s clamp is "a FIGHT-semantics ruling — Phase 5, plan 05-01 owns fight health";
  the fight slice's `shield` copy "ships now and its writer arrives with the phase that has a
  surface to spend from".
- The ops that **do** exist and could receive a confirmed transformation today are all
  **build**-slice writers: `setFactionAp`, `setUnitMaxHp`, `setUnitShield`, `setTally` /
  `nudgeTally`. The two fight writers that exist — `setUnitHp`, `setAlive` — need a fight.

**What's unclear:** ROADMAP criterion 4 requires firing to be demonstrable in this phase. If
confirm writes the **build** slice in setup, a fight action edits the allocation, which the
ROADMAP separates on purpose ("Editing the build mid-fight applies to the build rather than
retroactively to the fight in progress"). If confirm requires a fight, criterion 4 is only
demonstrable through the self-test, not by a student.

**Recommendation:** one op, `applyProposal(side, unitId, lines)`, one commit, one Ctrl+Z, writing
**whichever slice is live**: the fight slice when `state.fight !== null`, the build slice in setup.
Phase 3.1 does **not** ship a start-fight button (that is FIGHT-01). The setup path is then the
*rehearsal* — "what does my rule actually do to these numbers?" — which is a legitimate workshop
act and is one Ctrl+Z away. The consequence to put to the developer in one sentence: **in setup,
confirming a proposal edits the allocation.** If that is unacceptable, the fallback is to make
firing available only during a fight and to accept that criterion 4 is demonstrated by the gate
rather than by a student until Phase 5.

### OQ-2 — Health-key scope for the damage derivation: `hp` only, or `hp` + `shield`?

Both measured (§ D-14). `hp`-only recommended and reasoned; `hp+shield` gives ≈5 instead of ≈9 for
a shield-stripping action. This is a one-constant decision (`HEALTH_KEY` vs a `HEALTH_KEYS` array)
and can be made late, but it must be made **explicitly** and written down beside the constant,
because the next reader will otherwise "fix" it.

### OQ-3 — D-10's cap, priced

A compact positional spelling of one authored action — `Pounce~ap1~hp2~1hp-3` — is **20
characters** for a 6-character name; a name at the 24-code-point cap adds up to 18 more, so budget
**~38 characters worst case**.

| Authored per side | Both sides | Against SHARE-04's 512 budget, with 02.1's ~180 already claimed by token types |
|---|---|---|
| 3 | 120 (worst case 228) | comfortable |
| 4 | 160 (worst case 304) | tight at worst case |
| 6 | 240 (worst case 456) | **over budget with the vocabulary** |

**Recommend 3 per side.** It matches the shipped three per faction, makes D-07 concrete on screen
(3 shipped + 3 authored = 6 cards per column, all the same kind of thing), and leaves headroom.
Two notes for Phase 4: (a) if a student can edit a shipped action's `cost`/`req`/`xf`, the codec
must carry those too — encode **diffs from the default**, so an untouched shipped action costs ~0;
(b) CLAUDE.md's escalation path (`CompressionStream('deflate-raw')` + base64url, measured 1,165 →
167 chars, zero library bytes) raises the ceiling ~7× if the dial ever needs to move.

### OQ-4 — Does the admission line belong in the strip at all, or beside the action card?

Recommended in the strip (D-16 names PROJ-04's ignores box as "the natural home", and the measured
implementation puts it there with zero gate churn). The alternative — a note on the card of the
action that is not modelled — is more local but multiplies across up to 18 cards and puts
projection language into `[S06.1]`, which currently carries none. Not recommended, recorded so it
is not re-litigated.

**Field contract, each point measured:**

| Field | Type | Bound | Evidence |
|---|---|---|---|
| `cost` | array of `{ tok: string, n: integer }` | `n ≥ 1`; length 0 or 1 in v1 (D-01 says "a token type and an amount") | survives walk + round trip |
| `req` | array of `{ tok: string, n: integer }` | `n ≥ 0` | survives walk + round trip |
| `xf` | array of `{ who: 'caster'\|'target', tok: string, d: integer }` | `-MAX_ALLOC ≤ d ≤ MAX_ALLOC`, `d ≠ 0` | `Number.isInteger(-3)` is true; the walk accepts negatives; `requireDelta` already accepts them and refuses `-1.5` with the file's own message |
| all | JSON-clonable, integers-only | `Object.keys(build)` unchanged: `['schema','cats','mechs','tokens']` | 4 shipped rows pin it; nesting under `actions` touches none |

**A new signed bound is needed.** Every existing `int()` call site uses a floor of `0`. `int()`
compares rather than coerces, so `int(d, -MAX_ALLOC, MAX_ALLOC, 'a change to "' + name + '"')`
works unchanged — but the constant must be named and exported beside `MAX_ALLOC` / `MIN_UNITS` /
`MAX_UNITS`, for the reason those three are: *"one number in seven places, quietly waiting to
drift apart."*

**Do not use, measured:**

| Shape | Why it fails |
|---|---|
| `{ hp: 2 }` — an object keyed by token id | Re-opens the CR-02 key position. `bag['__proto__'] = {…}` reparents; `bag['constructor']` resolves to a function. |
| `Object.create(null)` as the mitigation | **Does not survive `thaw()`** — comes back a plain object with `Object.prototype` restored. |
| `new Map(...)` | Becomes `{}` through `thaw()` — silently, one commit later. |
| A `when: () => …` predicate | Dropped by `thaw()`; survives inside the frozen `cur` until the next commit and then simply is not. This is also the `eval`-adjacent shape the phase must refuse. |
| `{ cost: undefined }` | The key disappears entirely through `thaw()`. |
