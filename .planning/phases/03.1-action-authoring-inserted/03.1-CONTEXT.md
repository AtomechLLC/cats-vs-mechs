<domain>
## Phase Boundary

Actions stop being frozen data and become something a student programs. An action carries a **cost**
(consumed), **requirements** (checked, not consumed) and **transformations** (what changes, on whom,
by how much) — all expressed over the token vocabulary Phase 2.1 already made student-authored.

Requirements: ACT-01 through ACT-07.

Explicitly NOT in this phase:
- **The round loop** — declaring both sides' actions, pressing Advance, the history moving up and
  the changed-since-last-round display are FIGHT-12 through FIGHT-16 and belong to Phase 5. This
  phase makes actions *authorable* and *previewable*; Phase 5 is where a declared action lands.
- **The build code carrying authored actions** — SHARE-08, Phase 4.
- **Any automatic resolution.** See `<the_line_this_phase_walks>`.

</domain>

<the_line_this_phase_walks>
## Why this is not the thing PROJECT.md forbids

PROJECT.md's Out of Scope says: *"Automated combat resolution — Students adjudicate effects and
counters themselves; that adjudication is the exercise. An engine that resolved them would remove
the learning."*

A tool that applied transformations would be resolving. **This tool does not apply them.** The
student authors the rule; the tool reads that rule back and waits. Concretely:

- The tool **shows** what the student's own action says would happen — which tokens move, on whom,
  by how much.
- The student **accepts it, edits any number in it, or overrides it entirely.**
- **Nothing lands until they say so.**
- The tool never decides *whether* an action happens, *who* it targets, whether a counter applies,
  or what any of it is worth.

That is bookkeeping of a student's design, not a judgement about it — the same line the projection
already walks, and the same stance as "manual override is a primary interaction" in PROJECT.md's
Context section.

**This was the developer's explicit choice on 2026-08-28**, taken over auto-apply. Auto-apply would
have required rewriting the Out of Scope entry, and was declined. The Out of Scope list is therefore
**unchanged**, and this phase must not quietly erode it.

**If an implementation ever finds itself deciding something, it has left the phase.**

<decisions>
## Implementation Decisions

The developer supplied the shape of this feature directly and answered the one question that forks
it. D-01 through D-05 are theirs. The rest are Claude's discretion, recorded so downstream agents
build against them rather than each inventing an answer.

### The developer's specification (locked)

- **D-01:** An action carries a **cost**: a token type and an amount, **consumed** when the action
  fires. Default is one action point, matching what the shipped board already implies.
- **D-02:** An action carries **requirements**: token types and amounts that must be present for the
  action to be available, and that are **not** consumed. The example given was Health ≥ 2.
- **D-03:** An action carries **transformations**: each names **the caster or the target**, a token
  type, and the amount that token count changes by. An action may carry more than one.
- **D-04:** **The tool proposes; the student disposes.** *(Chosen explicitly over auto-apply and
  over check-only.)*
- **D-05:** The per-side **sequence** of actions is real and wanted, but lands in Phase 5 as
  FIGHT-12 — it is the fight loop, and this phase has no turn to hang it on.

### The round loop this feeds (developer, 2026-08-28) — and where this phase stops

- **D-05a:** The developer described the loop directly: **declare the actions for both sides**
  (with performer and target where the action needs them) → press **Advance** → the previous board
  state **moves up into a history** → the new state **shows what changed since the previous round**
  → declare again. Simultaneous declaration, one Advance for both sides, and a ledger that
  accumulates on screen. Recorded as FIGHT-12 through FIGHT-16 and written into ROADMAP § Phase 5.
  A round is a **round**; the developer rejected "Day".
- **D-05b:** **This resolves the blocking question about what "confirm" writes.** It writes on
  *Advance*, in Phase 5. So **this phase ships authoring and a preview, not an apply** — the
  student can see what their rule would do and edit the numbers in it, and Phase 5 is where a
  declared action lands. ACT-05 is therefore **half-delivered on purpose here**; the planner must
  say so rather than let a verifier read it as a gap.
- **D-05c:** **Damage spends shield before it reaches health**, and the split is shown rather than
  applied silently (FIGHT-16). This is the one resolution rule the developer specified directly,
  and it is the propose-not-decide line applied to a rule rather than to an action.

  ⚠️ **Assumption the planner must confirm or correct, stated because the projection numbers turn
  on it.** "Spends a point of shield before dealing damage" is read here as **damage applying to
  shield first, point for point, then overflowing to health** — 3 damage against 3 shield + 6
  health leaves shield 0 and health 6. The alternative reading, that one hit consumes exactly one
  shield point and then lands in full, is not what is assumed. This is a one-constant difference in
  `[S02]` and the research measured both shapes; it is flagged rather than buried.

### What an action is

- **D-06:** The record extends the shipped shape rather than replacing it. Today an action is
  `{ id, name, dmg, keywords }`. `dmg` and `keywords` stay for the shipped six, because Phase 3's
  reference cards and `bestDamage` both read them and Phase 5's adjudication still uses the
  keywords. Cost, requirements and transformations are **added**, not swapped in.
- **D-07:** **A shipped action and a student's action are the same kind of thing.** The six board
  actions should be expressible in the new form, and the authoring surface should not have a second
  tier for "real" actions. This is the same principle Phase 2.1 settled for token types, and the
  same reason its picker lists built-ins and custom types identically.
- **D-08:** **Transformations are signed deltas, not verbs.** "target Health −3", not "damage 3".
  A signed delta over an arbitrary token type covers damage, healing, shield, and every token a
  student invents, with one mechanism and no vocabulary of effects for the tool to interpret.
- **D-09:** **Actions live in the `build` slice**, alongside the token vocabulary they name, so a
  restyle and a re-authoring are the same kind of edit — undoable, and round-tripping through
  Phase 4's code (SHARE-08).
- **D-10:** **Cap the authored actions per side**, as Phase 2.1 capped token types at 6. The number
  is a Phase 4 codec dial; the planner should set it from measured encoding cost, not taste.

### Referential integrity

- **D-11:** **An action naming a removed token type is refused by name, with a message saying which
  action and which token** (ACT-07). Not silently skipped, and not fired with a missing term.
  Phase 2.1 established that a reveal naming a departed type is inert because nothing draws it — an
  action is different, because a missing term changes what the rule *means*.
- **D-12:** **Removing a token type that an action names must tell the student what it will break,
  before it happens.** Phase 2.1's removal is one undoable step with no confirmation, which was
  right when nothing referenced a type. Something does now.
- **D-13:** The id gate Phase 2.1 built — the named `RESERVED_KEYS` list, the shape pattern, the
  `hasOwnProperty` existence check — applies to action ids too. Its three layers were proven by
  peeling them one at a time; do not build a one-layer gate here.

### The projection

- **D-14a:** **Shield now soaks, per D-05c.** The earlier open question — health only versus
  health plus shield — is settled by the developer's rule: damage spends shield first. The
  projection's target pool is therefore health **and** shield, which is what `factionEhp` already
  computes. Research measured the shipped board at ≈5 turns under that reading rather than ≈9.
  **The teaching example changes, and that is the correct number rather than a regression** —
  the planner should expect the strip to move and update the phase's own fixtures.
- **D-14:** **`bestDamage` stops being well-defined and the planner must resolve it.** It is
  `max(action.dmg)` — one scalar per faction — and Phase 3's entire projection rests on it via
  `factionDps` → `turnsToWipe` → the strip. An action that costs two points, heals its caster, or
  moves a student-made token does not reduce to that.
- **D-15:** **Whatever replaces it must keep PROJ-06.** The projection may become less confident
  when actions are programmable — a range may widen, or the projection may honestly say it cannot
  model an authored action. **Saying less is allowed; implying a verdict is not.** The three-layer
  verdict gate is live and will catch comparative vocabulary reaching the page.
- **D-16:** If the projection cannot model an authored action, **it should say so plainly rather
  than silently ignore it.** A projection that quietly omits half the board is worse than one that
  admits its blind spot — that is the whole argument behind PROJ-04's "what this ignores" list,
  which already exists and is the natural home for the admission.

### Claude's Discretion

D-06 through D-16 are Claude's, and the planner may revisit any of them if research contradicts it.
D-14 in particular is flagged rather than answered: it is a real design question that deserves
research before a plan commits to it.

</decisions>

## Existing Code Insights

### Reusable assets
- `App.data.DEFAULTS[side].actions` — `{ id, name, dmg, keywords }` per action, six in total.
- `[S05]`'s authoring ops from Phase 2.1 — `createTokenType`, `renameTokenType`, `removeTokenType`
  and the three-layer id gate. Actions are the same problem with a richer record.
- `[S06.2]` the picker — a list-plus-editor over an authored vocabulary, with `pickerSig` keying its
  repaint. The action editor is that shape again.
- `[S06.4]` the reference band and the per-column action cards — already render actions, so they are
  the natural place an authored action becomes visible.
- `[S02] turnsToWipe` / `soakTotal` / `bestDamage` — what D-14 puts in question.
- `App.boot.wrap` — the listener boundary every handler must use.

### The gates you inherit
`node tests/selftest-node.cjs` runs **412** assertions, interaction gate **66 of 66**, stub-drift
**36 shell ids**. The artifact's full suite is **520** rows with a DOM — 108 only run with one.
**A green Node run is not full coverage.** Lift `makeStubDom()` at run time, run the artifact in a
`vm`, call `App.selftest.run()`, and supply `Event`/`MouseEvent`/`KeyboardEvent`. Assert the TOTAL,
not just `failed === 0` — a thrown suite skips its own state restore and silently changes figures.

### The naming trap
Both greps must stay at **zero** over `cats-vs-mechs.html`:

    grep -ci "counter\|rating\|balanced\|difficulty"
    grep -c "verdict\|balanced\|rating\|difficulty"

`counter` is banned; `encounter` is out; `rating` hides inside `generating` (write "generated"),
`operating`, `iterating`, `separating`, `enumerating`, `decorating`. It has fired seven times in
this project, twice via a comment quoting removed code. **Describe, never quote.**

**This phase adds a new hazard:** the natural word for what a transformation does to a target is
often a comparative, and the PROJ-06 verdict gate is live. Layer C walks every rendered string, so
any proposal text — "Mechs Lasers: target Health −3" — is checked. Keep the copy arithmetic, not
evaluative.

### The rule five agents learned the hard way
*If a probe passes when you expect red, the probe is wrong until proven otherwise.* Every wave of
Phase 3 found one of its own probes vacuous, and each finding improved the code. Two of Phase 3's
review findings were gates that could not fail.

<specifics>
## Specific Ideas

- The developer's own example is the acceptance test to build toward: **cost = 1 action point
  (consumed), requirement = 2 health (not consumed), transformation = target loses some amount of a
  resource.** If that action can be authored, fired, proposed and confirmed, the phase works.
- The proposal is the moment this phase either honours PROJECT.md or breaks it. It should read like
  a restatement of the student's own rule — "your Lasers says: target Health −3, caster Action
  Points −1" — not like an outcome the tool has computed.

</specifics>

<deferred>
## Deferred Ideas

- **The per-side action sequence** — FIGHT-12, Phase 5. Wanted, and named by the developer in the

- **Conditional transformations** ("if the target has Shield, instead…") — a rules language rather
  than a record, and a large step past what was asked for.
- **Actions that target multiple units** — the shipped model is one caster, one target.
