<decision_this_plan_makes>
**One new dialog, with two panes, not two dialogs.**

RESEARCH sketched the proposal as a second dialog (`#act-fire`) beside the editor. This plan ships
ONE dialog, `#act-edit`, carrying two panes: the authoring pane (this plan) and a proposal pane
(reserved here, filled by plan 03.1-07). Which pane is showing is a dataset attribute on the dialog
node, the same technique `[S06.2]` and `[S07.2]` both state for "which surface is showing what".

Three reasons, all of them costs avoided:
- One topbar button, one `LATE_BINDERS` entry, one delegated root, one signature. Two dialogs double
  every one of those.
- A modal opened from inside a modal stacks focus and close-request behaviour, and the stub has no
  close-request behaviour at all, so the stacking could not be exercised under Node.
- The id budget: the picker cost 19 of the file's 36 shell ids. One dialog with two panes lands near
  that; two dialogs land near forty.

**And the topbar button must be paid for consciously.** Phase 2.1 collapsed a ROW of topbar buttons
into one, precisely because the row grew by one control per invention. This adds a second permanent
button. That is a different thing from the row that was deleted — it is one, it is permanent, and it
is bounded — and the plan says so out loud here and requires the shell comment to say so too,
because the next reader will otherwise read the collapse as undone. It must not become
one-per-anything.
</decision_this_plan_makes>

<the_line_this_phase_walks>
This plan builds an AUTHORING surface. It has no Fire control, no proposal, and no apply. The
proposal pane exists as reserved markup that renders nothing. Nothing on this surface decides

refuse.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a press on the dialog -> an op | a delegated listener turns a control into a dispatch |
| a typed name -> `renameAction` | free text crosses into state |
| a student's word -> a rendered row | the list row's text is student-supplied |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03.1-18 | Tampering | a student string reaching a CSS class suffix or a selector | mitigate | `data-k` carries an id, never the value; every class suffix comes from an enumerated allowlist, as `safeShape` and `safeColor` already do |
| T-03.1-19 | Injection | a typed name reaching a markup sink | mitigate | `createElement` + `textContent` only; the document-wide `FORBIDDEN` scan enforces it and is a grep on this task |
| T-03.1-20 | Denial of service | a listener throwing outside the error boundary and leaving a dead surface | mitigate | every listener through `App.boot.wrap`; probe Q proves the check can fail |
| T-03.1-21 | Tampering | a stub whose dataset spelling differs from the shell, making every check green over nothing | mitigate | the stub is built from the shell's spellings and the bidirectional stub-drift gate covers both directions; probe O proves both |
| T-03.1-22 | Elevation of privilege | a rules language creeping into the editor | mitigate | the editor edits named fields only; there is no free-text field other than the name, and `eval`/`new Function` absence is a grep |
| T-03.1-SC | Tampering | npm/pip/cargo installs | accept | zero packages installed by this phase |
</threat_model>
