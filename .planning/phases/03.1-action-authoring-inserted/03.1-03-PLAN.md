<the_line_this_phase_walks>
No op in this plan applies a transformation. `createAction`, `renameAction` and `removeAction`
edit the DEFINITION of a rule. Nothing here spends a cost, checks a requirement against a unit, or
moves a token. `[S05]` reserves fight semantics to Phase 5 in writing three times already; this
plan adds nothing to that list and removes nothing from it.

**`eval` and `new Function` are banned.** An authored rule is a data record. A `when:` predicate, a
condition string, or any field the tool would have to interpret as code is refused by construction:
the ops write only the fields named here, field by field.
</the_line_this_phase_walks>

<decisions_this_plan_makes>
Both are forks the pattern map flagged and refused to settle. They are settled here, in writing,
beside the code:

1. **A shipped action can be renamed and re-costed, but not removed.** D-07 says a shipped action
   and a student's action are the same KIND of thing, and that is honoured everywhere else — one
   list, one editor, no second tier. Removal is the exception, for the same reason the five shipped
   token types cannot be removed: the reference band's relationship records name the six shipped
   actions by id, and a removed one would leave the band naming nothing. `removeAction` therefore
   keeps `removeTokenType`'s first arm, transcribed, refusing by the LIVE name.
2. **`renameAction` is a PLAIN commit; `createAction` and `removeAction` are structural.** A rename
   changes a label, and plan 03.1-04 makes an action's name a per-frame read on the card, exactly as
   a token type's name already is. A create or a remove changes how many cards a column holds, which
   is structure. Note the consequence for the suite: a build-time behaviour cannot be asserted with
   a rename, because a rename runs the sync pass and never the structural one.
</decisions_this_plan_makes>
