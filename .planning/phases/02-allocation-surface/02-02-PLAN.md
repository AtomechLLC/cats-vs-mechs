<open_questions_resolved>
Three of the phase's five open questions are answered here.

**Q-1 — does `shield` get a stepper in Phase 2? RESOLVED: YES, on the `build` slice only.**
Reasoning, stated because research left this genuinely open and `01-REVIEW-FIX` WR-07 flagged it
for a human decision that had not been made. ALLOC-04 puts blue shield squares on screen in this
phase, and a stat that is visible but uneditable is a workshop trap — a student sees three blue
squares on every Mech and has no way to touch them. `App.model.unitEhp` is literally
`maxHp + shield`, so an allocation surface that can edit only half of a unit's durability cannot
express the asymmetry the whole artifact exists to teach. The board's "3 shield per Mech" is a
number a student building a different faction would obviously want to change. This is a
deliberate reading of ALLOC-01 as "the student allocates a unit's durability", not a scope
expansion: the op is a five-line sibling of `setUnitMaxHp` and adds no new concept.

**The split that keeps this out of Phase 5's way:** `setUnitShield` / `nudgeUnitShield` write
`state.build[side].units[].shield` — the *allocation*. The `fight` slice's own `shield` copy
still has **no writer** and Phase 5 (plan 05-01) still owns it, exactly as WR-07 scoped. This
mirrors the shipped `setUnitMaxHp` (build) versus `setUnitHp` (fight) pair precisely. Write a
comment saying so, and name Phase 5's future op `setFightShield` in that comment so the next
planner does not collide.

**Q-5 — IN-01, `99` as a magic number. RESOLVED: hoist the constant, do not change the clamp
semantics.** `[S05]` defines `MAX_ALLOC = 99` and every existing `int(..., 0, 99, ...)` call
site uses it, along with the new ops. This is a pure rename with no behaviour change, done here
because this plan is already editing `[S05]` and doing it later means editing the same lines
twice. **Explicitly NOT fixed here:** `setUnitHp` clamping fight health to `MAX_ALLOC` rather
than to the unit's own `maxHp`. That is a fight-semantics decision and Phase 5 owns fight HP;
changing it now would silently alter behaviour in a phase that has no fight surface to test it
on. Record the deferral in the SUMMARY so it does not evaporate.

**Arrow-key repeat (D-17 versus the OS key-repeat rate). RESOLVED: option (b) from research §3
— honour D-17 literally.** On `keydown` with `e.repeat === false`, fire one step and start the
same ramp engine the pointer uses; on `keyup`, stop it; **ignore every `e.repeat === true`
event**. The OS repeat rate is neither 400ms nor 40ms and differs per machine, so accepting it
would make D-17's "held arrows use the same ramp as press-and-hold" false. The ramp engine is
therefore keyed by source (`'pointer'` / `'key'`) so a stuck key and a stuck pointer cannot both
be running.
</open_questions_resolved>

**`nudgeFactionAp(side, delta)`, `nudgeUnitMaxHp(side, unitId, delta)`,
`nudgeUnitShield(side, unitId, delta)`.** Each one:
- calls `requireSide(side)` **outside** the commit, so an unknown side throws before the funnel
  is entered and leaves no phantom undo step;
- rejects a non-integer delta with a `TypeError` naming it, before the commit;
- reads the current value and writes `int(current + delta, 0, MAX_ALLOC, …)` **inside** the
  commit mutator, so the read and the write are atomic. A 40ms ramp must never be able to
  double-apply a stale read;
- uses the **identical label string** as its absolute-set sibling — `'ap ' + side`,
  `'maxHp ' + side + '/' + unitId`, `'shield ' + side + '/' + unitId`. This is what D-10's
  500ms window keys on, and it is what makes a whole press-and-hold one Ctrl+Z (UX-01);
- **returns `true` if the value changed and `false` if it did not.** This is the sixth stop
  condition for the hold ramp (P-03). At 40ms/step a hold saturates at the clamp bound in about
  four seconds and would then issue roughly 25 no-op commits per second, each doing a full deep
  clone of state. Returning a boolean rather than throwing is deliberate: `App.boot.wrap` turns
  a throw into a visible error panel, and flashing that panel on every over-press during a live
  demo is worse than the no-op it is warning about.

**`setUnitShield(side, unitId, shield)` (Q-1).** A five-line sibling of `setUnitMaxHp`, writing
`s.build[side].units[…].shield` through `int(shield, 0, MAX_ALLOC, 'shield')`, label
`'shield ' + side + '/' + unitId`. Comment it as the *build*-slice writer and state that the
`fight` slice's `shield` still has no writer, that Phase 5 plan 05-01 owns it, and that its op
will need a distinct name such as `setFightShield` — the same build/fight pairing
`setUnitMaxHp` and `setUnitHp` already model.

**`addUnit(side)`.** `requireSide` outside the commit. Inside the mutator: throw
`'That side is full'` when `units.length >= MAX_UNITS`. Push a unit whose `maxHp` and `shield`

key on `id`, and `findUnit` returns the first match. `prefix + (length + 1)` collides after any

**Private `routeUi(btn, e)` — the branch the seam exists for.** It reads `btn.dataset.act`,
returns `false` at once when that act is not in `UI_ACTS`, and otherwise returns `true` after
calling `UI_HANDLERS[act]` when one is registered. `true` means *claimed by the UI layer*: the
caller must return without capturing the pointer, without starting a ramp and without ever
calling `App.ops.dispatch`. **Both entry points below call it first.** Skipping it on the
keyboard path is the same bug wearing a hat — Enter on a token-appearance button would reach
`dispatch` and raise the panel.

**`pointerdown` drives the steppers. This is the whole of ALLOC-07's count half.** The handler
finds `e.target.closest('[data-act]')`, returns silently when there is none, clears
`ui.kbdNav` if it is currently true, then calls `routeUi(btn, e)` and **returns immediately if
it claimed the press**. Only then does it call `setPointerCapture(e.pointerId)` on the button
so the matching up/cancel is guaranteed to reach the same element, fire step one immediately,
and start the hold ramp — the last of those **only when `HOLD_ACTS.indexOf(act) !== -1`**.

**`click` is bound too, but its body runs only when `e.detail === 0`.** That is how a
keyboard-activated click (Enter or Space on a focused button) presents, since `detail` is the
click count and there was no click. That body finds the same `[data-act]` element and calls
`routeUi(btn, e)` before `fire(btn)`, exactly as `pointerdown` does — a UI-only act has one
path per input method and **both** must return before `dispatch`.

A mouse click carries `detail >= 1` and was already served
by `pointerdown` — running here as well **doubles every press**, and this was measured: one
physical click with both handlers live produced two commits (P-01). It fails *upward*, which a
casual test misses. Write the reason as a comment above the `detail` test, because the line
looks like a spurious guard otherwise.
*Fallback if `detail` proves unreliable in a real browser:* set a transient flag in the
`pointerdown` handler, clear it on the next macrotask, and ignore `click` while it is up. Prefer
`detail` — it is stateless. If the fallback is taken, record it in the SUMMARY.

Do **not** drive steppers from `click` alone. A `click` fires only when `pointerdown` and
`pointerup` land on the same element, so any rebuild between them silently eats it — an
intermittent undercount, which is the trust-destroying kind (P-02).

**The ramp runs for steppers and for nothing else.** `startHold` is called only when the act
is in `HOLD_ACTS`. Without that gate the ramp starts for **anything** carrying `data-act`:
hold `Undo`, `+ Add Cat` or a per-unit remove for 400ms and it begins repeat-firing at up to
25 presses a second. The sixth stop condition below — the op returned `false` — cannot save
it, because only the `nudge*` ops return a boolean; `undo`, `addUnit` and `removeUnit` return
`undefined`, so the ramp would run until the pointer is released and then throw
non-terminally on the first bound it hits (roster full, one unit left, empty undo stack),
flashing the error panel mid-demo. Use the allowlist, not a `data-step` sniff — a future act
could carry a step and still not want a ramp.

**The hold ramp (D-18).** Private transient state — a source tag, the element, a timer handle
and a start timestamp. It never touches `App.state`; timer state is interaction state. Export
a read-only `holdSource()` on the frozen surface returning the live source tag (`'pointer'` /
`'key'`) or `null` when no ramp is running; it exists so the Node gate can assert *that no
ramp started* synchronously, instead of sleeping past `HOLD_FIRST_MS` in wall-clock time.
Self-rescheduling `setTimeout`, not `setInterval`, because the period changes. Named module
constants, all four exported on the frozen `App.interactions` surface so `[S09]` can assert
against them: `HOLD_FIRST_MS = 400`, `HOLD_STEP_MS = 120`, `HOLD_FAST_MS = 40`,
`HOLD_FAST_AFTER_MS = 1000`. Delay is `HOLD_FIRST_MS` before the first repeat, then
`HOLD_STEP_MS`, then `HOLD_FAST_MS` once elapsed passes `HOLD_FAST_AFTER_MS`.

**Write this comment next to `HOLD_FIRST_MS`, because it is the plan's least visible
constraint (P-05):** the largest gap between successive steps in a hold is `HOLD_FIRST_MS`, and
`App.state.COALESCE_MS` is 500 — a margin of 100ms. Raising `HOLD_FIRST_MS` above
`App.state.COALESCE_MS` turns a single press-and-hold into many undo entries and blows the
30-deep stack. `COALESCE_MS` lives in `[S03]` and **no Phase 2 plan owns it**, so the constraint
is one-directional: this number moves down, never up. Phrase the comment with *accelerates* or
*acceleration*, never *accelerating* — `rating` is a substring of that word and it fails the
acceptance grep.

**Six stop conditions, all of them.** `pointerup`, `pointercancel`, `lostpointercapture`,
`window` blur, `document` visibilitychange — and the sixth: stop when the op returns `false`
(clamped, nothing moved). Missing `pointercancel` / `lostpointercapture` is the classic
press-and-hold bug — a hold that leaves the window never stops, and the first thing the student
sees is health pinned at 99 (P-03).

**`fire(btn)` is dispatch, not arithmetic.** Read `dataset.act`, `dataset.side`, `dataset.unit`,
`dataset.step`, convert the strings explicitly with `Number(...)` at this one call site (the
`int()` comment assigns the conversion here), and call `App.ops.dispatch(act, payload)`. Return
the op's boolean so the ramp can read it.

**The numeric field (ALLOC-03, D-14 through D-17).** The element is
`type="text" inputmode="numeric"`, which 02-01 rendered — `type="number"` is **spec-blocked**
for D-15: the HTML "valid floating-point number" production does not admit a leading `+`, and
the number state's value sanitisation sets the value to the empty string when it is not valid,
so `+5` reads back as `""`. `setSelectionRange` also throws on `type=number`, which would make
caret restore across a rebuild impossible.

Private `FIELD = /^([+-]?)(\d{1,3})$/` and `parseField(raw)` returning
`{ ok, kind, n, why }`. A regex, not `Number()` / `parseInt()` / `Math.trunc()`, because those
fail *silently*: `''` and `'  '` become `0`, `'1e3'` becomes `1000`, `'0x5'` becomes `5`,
`'Infinity'` becomes `Infinity`, `'5.5'` becomes `5.5`. The empty-string case is the dangerous
one — a student who selects-all, hits Delete and clicks away would commit **0 health**.
`{1,3}` caps at 999 and `[S05]`'s `int()` then clamps to `0..MAX_ALLOC`; parse and clamp stay
separate, because `-12` from a current 3 legitimately yields `-9` and clamping is not the
parser's job. Refuse with this file's own readable messages —
`'that field was empty'` and `'type a whole number, or +5 / -8 to adjust'`. `int()` stays the
backstop, not the front line: its own refusal reads `Expected a whole number for health, got
null`, because `JSON.stringify(NaN)` is `null`, and that string means nothing to a student on a
projector (P-13).

Event handling on the field, exactly:
- `focus` — record `el.dataset.was = el.value`, then select all so typing replaces.
- `input` — **nothing**. Committing per keystroke would pass `12` through `1` and set health to 1.
- `keydown` Enter — parse and commit, keep focus.
- `keydown` Escape — restore `el.dataset.was`, do **not** commit, `preventDefault()`.
- `keydown` ArrowUp / ArrowDown — `preventDefault()` so the page does not scroll, then step by

  `<open_questions_resolved>` for why the OS repeat rate is not acceptable here.
- `blur` — parse and commit; on a refusal restore `dataset.was` **silently** rather than opening
  the error panel. A student clicking away from a half-typed value is not an error.
- A leading sign routes to the matching `nudge*` op; no sign routes to the matching absolute
  setter. That routing is the only decision `[S07]` makes about the number.

Because a rebuild can land between events, always re-read `dataset` off the element the event
actually arrived on. Never cache a node across frames.

**`ui.kbdNav`, the writer.** On the first `keydown` that is Tab, an arrow, Enter or Space, if
