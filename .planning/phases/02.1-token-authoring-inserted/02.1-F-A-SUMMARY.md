# Phase 2.1 Finding A: Revealing a Tally That Has Never Been Written Summary

**A student-made type's zero line now stays on the board while that type is open in the editor, and goes away again when they shut it — so the 36 controls that were built behind a hidden ancestor are all reachable by the finding's own metric, measured 36 of 36 against 3 of 36 with the change reverted. The board is still clean at rest, built-in types are untouched, and Ctrl+Z does not toggle a reveal. It does NOT finish the job: the editor is a modal dialog, so a pointer still lands on its backdrop rather than on the revealed stepper, and that is raised below as F-02.1-B with its own measurement.**

## What was asked and what was built

Finding **F-02.1-A** said a tally that has never been written cannot be raised anywhere on the page: the stat line is built on every card, `sync()` hides it at zero, and the stepper lives inside that line. The user chose option **(a)** — reveal the line while its type is selected in the editor — because it preserves **D-04**, the board being clean at rest.

Built exactly to the four points of the brief:

| Point | Where | What landed |

## F-02.1-B — the editor is modal, so the revealed control still cannot be pressed

**Raised here, measured, and NOT fixed — it is a design question, the same shape as the one that produced F-02.1-A.**

The picker opens with `showModal()`. A modal `<dialog>` is promoted to the top layer and its backdrop covers the viewport, so while it is open the rest of the document is inert. Measured, in Chrome, with the reveal working:

- `document.elementFromPoint` at the centre of a revealed stepper button returns the **dialog**, not the button — for all 36 controls;
- `button.focus()` on a board control does not move `document.activeElement` off the dialog;
- and when the student closes the editor to reach the board, the reveal clears and the line goes back to hidden.

So the student can now **see** their new type appear on all twelve cards the moment they make it, which is a real discoverability gain and was the visible half of what they needed. They still cannot **press** it. ROADMAP § Phase 2.1 criterion 3 — "a tally the student increments by hand" — is therefore **still not reachable through the shipped UI**, and `ALLOC-11` should stay unticked.

This was not knowable from the finding as written: its table measures "reachable (no hidden ancestor)", and by that metric the finding is closed. Modality is a second gate behind the first one, and nothing in this repo could have caught it — there is no layout engine in the Node gate and the in-file suite does not open the dialog modally.

**Three repairs, none chosen here.** The reveal machinery is the foundation for all three, so none of this work is wasted whichever way it goes:

- **(i) Open the editor non-modally** (`show()` rather than `showModal()`). The board behind it stays live, the revealed stepper is genuinely pressable, and "closing returns the board to clean" survives untouched. This is the only one that satisfies option (a) as the user described it. Cost is real: focus trapping, the Escape/cancel contract, and `[S08]`'s "close the modal before raising the error panel" behaviour (gate check 24) all rest on the dialog being modal.
- **(ii) Let the reveal outlive the close**, until the type's tally stops being zero or another type is revealed. One line change to `onPickerClose`. Cost: the board carries up to twelve zero lines for the one type a student just made until they use it — which is option (b) from the finding narrowed to a single type, and (b) was rejected.
- **(iii) Option (c) from the finding** — a tally control inside the editor. Rejected by the user, and re-listed only so the choice is complete.

**Recommendation: (i).** It is the only one that delivers what option (a) was chosen for, and the cost is bounded and testable — the gate already has a check covering the error-panel-over-modal case, so the regression risk is instrumented rather than unknown.
