## Accomplishments

### Task 1 — create and remove (`2960e8c` RED, `5b590ef` GREEN)

**`createTokenType`** validates the name through `requireTokenName`, then shape, colour, glyph and
scope against the shipped allowlists, each refusal naming the value it refused. The id is produced
by `nextTokenTypeId` and then confirmed by `requireNewTokenId` — the double call is deliberate, so
a later change to either one cannot quietly widen the other. It commits through `commitStructural`
with the label `'token new t<N>'`, because `buildColumn` decides whether this type's stat line
exists at all and `sync()` can neither create a line nor remove one. The record is assigned field
by field, never through a merge helper. It returns the produced id, so `[S07.2]` can select the new
type the moment `dispatch` returns.

**One guard sits inside the commit** — the `MAX_CUSTOM_TYPES` cap — because it needs the key count
from the detached copy. That is `addUnit`'s documented `MAX_UNITS` exception, and the comment says
so and says why it is safe (a mutator that throws leaves no trace). An assertion checks the
consequence rather than trusting the note: `undoDepth()` is unmoved after the cap refusal.

**`removeTokenType`** refuses the five built-ins FIRST, reading the **live** record's name so a
student who renamed Health to Vigor is told about Vigor, and offering rename as the supported
alternative (D-15). Then `requireTokenId`. Then one `commitStructural` mutator that checks the id
names something, deletes the vocabulary entry, and walks both sides calling `dropTally` on the
faction and on every unit. One mutator is one snapshot is one Ctrl+Z (D-16). There is no
confirmation dialog anywhere near it (D-17).

**`sideFromBuild` now records why tallies do not enter the fight slice** — a tally is a build-time
annotation this phase, and whether one should be spendable during a fight is Phase 5's ruling. It
is written down rather than left for the next reader to wonder whether somebody forgot it.

### Task 2 — rename and the sparse tallies (`6b16f8f` RED, `4cd5b45` GREEN)

**`renameTokenType`** gates the id BEFORE the read-then-write, which is the entire Pitfall 2
defence: `var t = tokens[id]; t.name = x` for a reserved id resolves `t` to `Object.prototype`.
It returns `false` and commits nothing when the trimmed name already matches. Plain commit, label
`'token rename ' + tokenId`, so typing coalesces into one undo entry.

**The tally trio.** `tallyBag` / `readTally` / `writeTally` hold the two sparse rules, with the
delete path delegated to `dropTally` so one place knows how a tally disappears rather than two that
have to agree. `hasOwnProperty` on every read.

**Two more guards, both outside the commit.** `tallyType` refuses an id that names no live type and
refuses a built-in by name. `tallyOwner` rules on whether the arguments agree with the scope chosen
at creation (D-01, D-03) and resolves the record that carries the number — called once on the live
board, where it is the guard, and again on the detached copy inside the mutator, where the first
call has already ruled.

**`setTally`** reads outside the commit and skips committing entirely when nothing would change;
**`nudgeTally`** reads and writes inside one mutator, because a 40ms ramp must never act on a
number it read a step ago. Both go through `tallyLabel`, so a press-and-hold on a tally stepper
collapses into one Ctrl+Z exactly as every other stepper on the board does.

**Pitfall 13 is an assertion, not a comment.** `addUnit` was deliberately left alone; the rule is
about *not* writing a line, so a row writes a tally on the last cat, adds a unit, and checks the
new one carries no bag while it does inherit the health it was seeded from.

## Deviations from Plan

### 1. [Rule 1 - Contract] A tally above `MAX_ALLOC` is clamped, not refused

- **Found during:** Task 2, writing the value-boundary rows
- **Issue:** the plan's `<behavior>` block says "`setTally` with `n` above `MAX_ALLOC`, or
  non-integer, is refused by `int`". `int()` does not refuse an out-of-range whole number — its own
  comment states the opposite in as many words: *"Clamping is for a whole number that is merely out
  of range; a non-number and a fraction are caller mistakes and throw."* Every other allocated
  quantity on the board (`ap`, `maxHp`, `shield`, fight `hp`) clamps.
- **Resolution:** the shipped semantics were kept and the assertion was written to them —
  `setTally(..., MAX_ALLOC + 40)` lands at `MAX_ALLOC`, and `2.5` and `'3'` both throw. Refusing an
  out-of-range tally would have invented a second boundary semantics for tallies alone, which is
  exactly the drift `MAX_ALLOC` was named to prevent.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `4cd5b45`

### 2. [Rule 2 - Correctness] Two guards the plan did not name: `tallyType` and `tallyOwner`

- **Found during:** Task 2
- **Issue:** the plan spells `setTally`'s guards as a sequence inside the op, and then spells the
  identical sequence again for `nudgeTally`. Written twice, the two would drift — and one of them
  is the security guard.
- **Fix:** the resolution is two named helpers called by both ops. `tallyOwner` is additionally
  called a second time inside each mutator, on the detached copy, where it cannot throw because the
  outside call has already ruled. That is the only way to have the guard outside the commit and the
  write inside it without resolving the record twice by hand.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `4cd5b45`

### 3. [Rule 3 - Test infrastructure] `[S09.7]` restores the board mid-suite

- **Found during:** Task 2 RED
- **Issue:** the create/remove block leaves six student-made types and a full undo stack behind it.
  The tally rows need a known vocabulary and readable `undoDepth()` numbers.
- **Fix:** `App.state.restore(savedAll)` + `flush()` runs once between the two blocks, with a
  comment saying why. `restore()` clears the undo stack, which is what makes the second block's
  depth rows mean anything. The suite's closing `restore` + round-trip row is unchanged.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `6b16f8f`

### 4. [Extra evidence] Both red probes were run graded, not once

- **Found during:** Task 1 and Task 2 acceptance
- **Issue:** the prescribed single-layer probe leaves the suite fully green on both paths, exactly
  as plan 02.1-01 warned. On its own it is not evidence.
- **Fix:** each probe was run twice, peeling one layer per run, until an assertion went red. Probe B
  observed real, persistent `Object.prototype` pollution. All eight counts are in the table above.
  The file was restored with `git checkout -- cats-vs-mechs.html` and re-verified green both times.
- **Files modified:** none (all probes reverted)
- **Commit:** n/a

## Notes for the next plans

1. **`readTally` is private on purpose.** `02.1-03`'s `amountFor` branch should follow
   `02.1-RESEARCH.md` § "The tally read", which reads the build slice directly at render time.
   Derived values are computed at render and never stored (CLAUDE.md), and a tally read is one
   `hasOwnProperty` pair — exporting an op for it would put a state-layer function on the render
   path for no gain.
2. **`tallyLabel(side, unitId, tokenId)` is the coalescing key.** A tally stepper in `[S07]` gets
   press-and-hold as one Ctrl+Z for free, and only if both ops keep using it.
3. **`scope` decides the render site**, and `tallyOwner` is where that decision is already written
   down — `'side'` means the faction record and `unitId` must be null-ish, `'unit'` means a real
   unit. `02.1-03` should mirror it rather than re-derive it.
4. **`createTokenType` returns the produced id.** `[S07.2]` can select the new type in the list the
   moment `dispatch` returns, with no re-derivation.
5. **Pitfall 12 is still owed.** `fire()` carries `{ side, unitId, delta }` and a tally stepper
   needs a fourth key. `02.1-03` or `02.1-05` pays the one `[S07.1]` exception.
