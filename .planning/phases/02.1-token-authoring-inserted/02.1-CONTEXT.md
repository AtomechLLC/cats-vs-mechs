# Phase 2.1: Token Authoring (INSERTED) - Context

**Gathered:** 2026-08-27
**Status:** Ready for planning

<domain>
## Phase Boundary

The token vocabulary stops being ours and becomes the student's. This phase delivers a **name** on
every token type, and the ability for a student to **create and remove token types of their own** —
types that count nothing on their own and carry a tally the student increments by hand.

Requirements: ALLOC-10, ALLOC-11.

Plan split from ROADMAP.md — section ownership is binding, since everything lives in one file:
- **02.1-01** owns the `[S01]` vocabulary changes (name field, open id space, id-shape validation
  replacing the fixed `TOKEN_IDS` allowlist) and the `[S05]` create / rename / remove ops
- **02.1-02** owns the authoring surface — the name field, the create and remove flows in the
  picker, and the board rendering student-created types

Explicitly NOT in this phase: making custom tokens round-trip through the build code (that is
Phase 4's SHARE-08, whose scope this phase enlarges), the projection or reference material
(Phase 3), and anything in the fight loop (Phase 5). A custom token is inert bookkeeping — the
tool never infers what one means.

</domain>

## Implementation Decisions

The user opted to skip the discussion round for this phase. All four gray areas below were
resolved at Claude's discretion and are recorded so downstream agents build against them rather
than each inventing an answer. **D-06 is the one where the user is the real authority** and is

### Locked upstream — do not re-litigate

From Phase 2's CONTEXT and what actually shipped:

- **D-00a:** Tokens are data — `{ shape, color, glyph }` per type — and the renderer is already
  vocabulary-driven. This phase adds fields to that record; it does not change the approach.
- **D-00b:** Every emoji pairs with a shape and colour that carry the meaning on their own. Emoji
  render from OS-supplied fonts and will not match across a classroom.
- **D-00c:** Token appearance lives in the `build` slice, so every change here is undoable through
  `commit` (not `commitUi`). New types and their tallies inherit this for free.
- **D-00d:** The glyph set is curated, not free text — measured at 12–30 chars per emoji against
  Phase 4's 512-char budget.
- **D-00e:** A student-created token **counts nothing on its own**. It carries a tally the student
  increments by hand. The tool tracks the number and never infers what it means. *(User's decision,
  taken when this phase was created.)*

### Where a custom token's tally lives

- **D-01:** **The student chooses the scope when creating the type — per-unit or per-faction.** The
  ROADMAP criterion says "per-unit or per-faction" and left it open deliberately. Both patterns
  already exist on the board: `hp` and `shield` are per-unit, `ap` is per-faction. Forcing one
  would make half of plausible student inventions awkward — "poison on *that* cat" is per-unit,
  "objective markers" is per-faction.
- **D-02:** **This is cheap specifically because both render sites already exist.** `[S06]` already
  renders a faction-level quantity at `side + '/ap'` and per-unit quantities in the unit card rows.
  A scoped custom type reuses whichever insertion point its scope names. Adding one `scope` field
  to the type record buys real flexibility without inventing a new layout.
- **D-03:** **Scope is fixed at creation and cannot be changed afterwards.** Changing it would
  orphan every tally already recorded under the old scope, which needs migration semantics nobody
  will remember at a workshop. Removing the type and creating a fresh one is the supported path,
  and the tallies are trivially re-entered.
- **D-04:** **Tallies default to zero and are stored sparsely.** A type that has never been
  incremented on a given unit stores nothing. This matters for Phase 4: 9 Cats × 6 custom types is
  54 potential numbers, and almost all of them will be zero in a real build.

### Reaching the editor

- **D-05:** **Collapse the four topbar buttons into one "Tokens" button.** Today `#topbar` carries
  four `openTokenPicker` buttons, one per built-in type. That does not survive students inventing
  types — the bar grows without bound, on a projector, which is the one place UX-02 says it must
  not. One button opens the picker; the picker shows **every** type, built-in and custom, as a
  selectable list with the editor beside it, plus a "New token type" affordance.
  This bounds the topbar at one button permanently and solves reachability for custom types
  properly rather than bolting a second mechanism onto the board.
- **D-06:** ⚠️ **Needs user confirmation.** D-05 changes UI that Phase 2 shipped and a human
  approved. The four separate buttons are gone, replaced by one. The behaviour is strictly better
  and the phase is closed rather than frozen, so this is legitimate forward work — but it *is* a
  visible change to something already signed off, so the planner should surface it rather than let
  it arrive as a surprise at the next rehearsal.
- **D-07:** **A shipped test asserts the old count and must be updated in the same plan that
  changes the topbar.** `grep -c 'data-act="openTokenPicker"'` currently returns 4 by design, and
  `02-03`'s acceptance record names that number. When 02.1-02 collapses the buttons, that
  assertion goes red. **That is the gate working, not a regression** — update it in the same
  commit, and do not "fix" it by leaving the four buttons in place.
- **D-08:** **No board-side edit control.** Phase 2 established this (duplicate `data-k` values on
  the board would break `withPreservedFocus`'s first-match restore). Custom types do not get an
  exception.

### What a name means

- **D-09:** **The name is a display label. The id remains the identity and is never shown.**
  `hp`, `ap`, `shield`, `dmg` and `dead` are load-bearing in `[S05]`, `[S06]` and the model — a
  rename must not touch them.
- **D-10:** **Built-in types can be renamed.** A student calling Health "Vigor" is exactly the
  authorship this phase is for, and it changes the label and nothing else.
- **D-11:** **Names need not be unique.** Two types called "Poison" are confusing but not
  corrupting, since the id disambiguates. Enforcing uniqueness would add a validation path and an
  error message for a harmless case; a workshop tool should spend its error messages on things that
  actually break.
- **D-12:** **Names are capped at 24 characters and restricted to a printable allowlist.** The name
  rides in the Phase 4 build code, so an unbounded string is a budget hole and an injection surface.
  The cap is a Phase 4 tuning dial, like `--tok` was for Phase 2.
- **D-13:** **A new type's id is generated, never derived from its name.** Deriving an id from user
  text reintroduces exactly the collision-and-prototype-key problem criterion 5 exists to prevent.
  Generate from a monotonic sequence (`t1`, `t2`, …) — see the naming trap in `<code_context>`
  before writing that code.
- **D-14:** **Id validation replaces membership validation, and must still refuse by name.**
  `TOKEN_IDS` is currently a frozen five-item allowlist, and that allowlist *is* the CR-02
  prototype-pollution defence. Opening the id space means validating the *shape* of an id instead
  (a short lowercase-alphanumeric pattern), and explicitly refusing `__proto__`, `constructor`,
  `prototype` and collisions with the five built-ins — with a message naming what was refused, not
  a silent drop. This is ROADMAP criterion 5 and it is a security criterion, not a polish one.

### Removal and its blast radius

- **D-15:** **The five built-ins cannot be removed.** The rest of the board binds to them. Attempting
  it is refused by name, same as an invalid id.
- **D-16:** **Removing a custom type removes its tallies with it, as one undo entry.** Ctrl+Z
  restores the type and every tally together. This falls out of D-00c for free.
- **D-17:** **No confirmation dialog on removal.** Because D-16 makes it a single undoable step, a
  modal would cost an instructor a click mid-demo to protect against something Ctrl+Z already
  covers. Contrast reset-to-defaults, which Phase 4 *does* confirm — that one is broad and
  destructive; this one is narrow and reversible.
- **D-18:** **Cap custom types at 6, and treat the cap as a Phase 4 dial.** Six types at roughly
  30 chars of definition each is ~180 chars before any tallies, against a 512-char design target
  that already carries the roster. Ships at 6; Phase 4 owns re-tuning it against measured codec
  output, exactly as `--tok` ships as a rehearsal dial for the projector.

## Existing Code Insights

### Reusable Assets
- `App.data.DEFAULTS.tokens` (`cats-vs-mechs.html:735`) — the five token records, each
  `{ shape, color, glyph }`. This phase adds `name` and, for custom types, `scope`.
- `App.data.SHAPES` / `COLORS` / `GLYPHS` (`:625`–`:658`) — the allowlists a new type draws from.
  Criterion 2 says custom types use the same ones, so nothing new is needed here.
- `App.data.TOKEN_IDS` (`:627`) — the frozen five-item allowlist that becomes id-shape validation
  under D-14. This is the CR-02 defence; changing it is the security-sensitive edit of the phase.
- `App.ops.setTokenStyle` — the shipped write path, already allowlisting its key *before* it
  indexes state. The create/rename/remove ops should copy that ordering exactly.
- `[S07]`'s `UI_ACTS` / `UI_HANDLERS` / `LATE_BINDERS` seam — built in Phase 2 precisely so later
  phases add UI-only actions without touching `[S05]`. A "new token type" action lands here.
- `[S06]`'s two render sites — `side + '/ap'` (`:1841`) for a faction-level quantity and the unit
  card rows for per-unit quantities. D-01's scoped tally reuses whichever its scope names.
- `MAX_ALLOC = 99` (`:1163`) and `COMPACT_AT = 12` (`:1661`) — the existing bounds a tally should
  respect rather than inventing its own.

### Established Patterns
- Namespaced IIFE per section returning `Object.freeze({...})`; cross-section references resolved
  at call time as `App.x.y()`, never captured at section-body scope.
- All page text via `createElement` + `textContent`. The forbidden-pattern scan covers
  `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `srcdoc`, `DOMParser` and bare
  `Function(` across the whole document.
- `commit` vs `commitUi` are the two greppable write paths; which one you call *is* the answer to
  "is this undoable?".
- `node tests/selftest-node.cjs` is the gate: currently exit 0 at **145 passed / 0 failed**, plus
  an interaction gate at **27 of 27** and a bidirectional stub-drift gate over 28 shell ids. Add
  assertions; never remove them.

### The stub-drift gate will fire, by design
`KNOWN_IDS` in `tests/selftest-node.cjs` is a hard gate in **both** directions — the run fails if
the shell carries an id the stub does not build, *or* the reverse. Any new picker element added by
this phase must be added there in the same commit, or the suite goes red. That is the gate doing
its job; it was made bidirectional in Phase 2 precisely because a silently-skipped picker path let
two bugs ship.

### Naming trap — this phase is unusually exposed to it
Two acceptance greps must stay at **zero** over `cats-vs-mechs.html`:

- `grep -ci "counter\|rating\|balanced\|difficulty"`
- `grep -c "verdict\|balanced\|rating\|difficulty"`

**This phase's whole subject is counting, and `counter` is a banned substring.** Do not name
anything `counter`, and do not write "a counter" in a comment — use *tally*, *count*, *running
total* or *sequence*. `rating` also hides inside `accelerating`, `generating`, `operating`,
`iterating` and `integrating`. The trap fired three times in Phase 2 wave 1 and once in wave 2,
caught each time only by re-running the greps after writing. Re-run both after every comment.

<specifics>
## Specific Ideas

- The picker becoming a list-plus-editor (D-05) is the structural change that makes this phase
  coherent. Built-in and custom types should look identical in that list — the point of the phase
  is that a student's invention is a first-class citizen, not a second tier below ours.
- A custom type with a zero tally everywhere should render as nothing on the board, not as a row of
  empty slots. The board stays clean until the student actually uses their invention.
- The refusal message for criterion 5 should name what was refused and why in plain words, since
  the audience is a student who typed something reasonable, not a developer reading a stack trace.

</specifics>
