## Accomplishments

### Task 1 — labels become sync-driven, and `amountFor` learns a scope (`716c941` RED, `7d813fc` GREEN, `3abf8a2` fix)

**`labelFor(state, tokenId)`** sits immediately beside `styleFor` and is written as its twin: the same `Object.prototype.hasOwnProperty.call` on the vocabulary, for the reason `styleFor`'s comment already gives, plus a `typeof … === 'string'` check on the record's `name` so a record that survived a Phase 4 decode without one still paints something readable. Fallback is `App.data.DEFAULTS.tokens.hp.name`.

**`statLine` gained an optional fifth argument** — the token id the label names — written through `setData` as `lbl`. `setData` already skips `undefined`, so the four-argument call sites are unchanged in behaviour. The literal label is still passed either way, so the first painted frame is never blank; for the shipped five the sync pass then overwrites it with the same words.

**The `[data-lbl]` pass** was added to `sync()` beside the `.brd-value` pass and written line for line like it. Its comment records why the label is not baked into `structure()`: a rename is a plain commit, and making it structural would rebuild both columns on every keystroke of a name being typed, discarding the caret and every token node. It is also what lets a rename of one of the five the board is built on (D-10) travel exactly the path a student-made one travels.

**`amountFor` gained its scoped-tally arm as a REORDER.** The three built-in labels (`ap`, `hp`, `shield`) now pass their token ids into `statLine`.

### Task 2 — the two render sites, and the collapsed zero (`8b83f4b` RED, `7e50e99` GREEN)

**`tallyLine` / `tallyLines`** — one builder, not two. The two sites differ in exactly two values (the key and the unit id), and a second copy would be a second place for the Tier-1 `data-k` contract to drift. `tallyLines` reads the scope off the record, because D-01 already put the decision there; a null unit id **is** the faction site. The five the board is built on are skipped by name.

`factionHead` draws the `scope: 'side'` lines directly after the action-point line and **before** the Damage and Total-health readouts. `unitCard` draws the `scope: 'unit'` lines after the shield line. Every new line carries `brd-line--opt` plus the type, the side and (unit only) the unit.

The stepper is built with `act: 'tally'`, `nudge: 'nudgeTally'`, `amt: <token id>`, and a key of `side + '/' + tokenId` or `side + '/' + unitId + '/' + tokenId`. Both shapes are unique document-wide by construction, for the same reason the shipped keys are: no unit is on two sides.

**The hide pass** walks `.brd-line--opt` after the `.tok-row` pass and sets `node.hidden` from `amountFor(...) === 0`. Order matters — the rows are reconciled first, so a line that unhides already holds the right content.

**`[C03]` gained one rule**, `.brd-line--opt[hidden]{display:none}`, matching the file's own two existing instances at `.err-panel[hidden]` and `.st-report[hidden]`. No twin rule was added for the dead `.unit-line` class, and the acceptance grep is at **0**.

## Deviations from Plan

### 1. [Rule 1 - Bug] `FIELD_OPS.tally.set` is `'setTally'`, not the plan's `'tally'`

- **Found during:** Task 3, before writing the entry
- **Issue:** the plan spells the row verbatim as `{ set: 'tally', nudge: 'nudgeTally', amt: null }`. `applyField`'s absolute branch dispatches `fieldOp(el, 'set')`, and `[S05] dispatch` carries `case 'setTally'` (`:2156`) and **no** `case 'tally'`. The plan's literal would therefore have reached dispatch's `default: throw` arm and shown a student the styled error panel the first time they typed a number into a tally field and clicked away.
- **Fix:** the row names the real op. Everything else about the entry is as the plan wrote it, including `amt: null` and the `|| d.amt` fallback. An `[S09.7]` row asserts the op name explicitly — *"and it names the real op rather than a spelling of its own"* — so the mistake cannot be reintroduced silently. Measured working end to end: typing `9` into a tally field and blurring lands 9 in state.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `da34c96`

### 2. [Rule 2 - Missing critical functionality] The stepper's `+` and `−` buttons now carry `data-amt`

- **Found during:** Task 3, tracing the plan's own edit 1 to its consumer
- **Issue:** the plan adds `tokenId: d.amt` to `fire()`. `fire()` reads `btn.dataset` off the node the press arrived on — and a press arrives on a **button**, never on the field. `stepper()` wrote `amt` onto the field only (`:2365`), so on a tally stepper every click and every hold would have dispatched `nudgeTally` with `tokenId: undefined` and thrown. The plan's must-have truth *"a tally stepper behaves like every other stepper: click, delta typing, arrow keys, press-and-hold ramp"* would have been false for two of the four.
- **Fix:** `amt: spec.amt` added to the `setData` calls for both buttons. Inert for the three shipped steppers: every reader of `data-amt` is scoped to `.stp-field`, `.brd-value` or `.tok-row` by class, and a `.stp-btn` is none of the three — verified by grepping every `dataset.amt` and `[data-amt` reader in both files. Measured after the change: `+` steps 2 -> 3, `−` steps 3 -> 2, twenty presses land twenty steps as one undo entry.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `da34c96`

### 3. [Scope boundary] `grep -c "FIELD_OPS\[d.act\].amt || d.amt"` returns 1, not the 2 the plan expects

- **Found during:** Task 3 acceptance
- **Issue:** the plan says to "change the two `.amt` lookups". There is **one**. Every reference to the table is at `:3318` (`FIELD_OPS[act][which]`, generic — it never names `amt`), `:3348` (`showFieldValue`, the only `.amt` read) and `:3782` (the new read-only export). `nudgeField` and `applyField` name their op through `fieldOp`, not through `.amt`.
- **Resolution:** the single site was changed and the criterion's intent is met — every read of a field's quantity now falls back to the node's own `data-amt`. A helper was briefly written to satisfy the count and then removed: a one-line abstraction over a single call site would have been shape without substance, and the count is not what the criterion is protecting.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `da34c96`

### 4. [Rule 1 - Bug in my own assertion] The no-rebuild row was measuring the suite's structural debt

- **Found during:** Task 1 GREEN, first stub-DOM probe run
- **Issue:** the row captured a `.unit-card`, renamed, flushed, and compared node identity — and read **red**. The rename was not the cause. `createTokenType` above it is a `commitStructural`, and the block then called `App.render.structure()` and `sync()` by hand, which paint the board but never clear `[S03]`'s `structural` flag. The next `flush()` therefore rebuilt both columns for a reason the rename had nothing to do with. Left as written, the row would have been either permanently red or — worse, had the ordering differed — permanently green for the wrong reason.
- **Fix:** `App.state.invalidate({ structural: true })` + `flush()` instead of the two hand calls, with a comment recording the measured red. This is exactly the class of thing the probe exists to catch, and it was caught by observation rather than by reasoning.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `3abf8a2`

### 5. [Rule 3 - Blocking] `FIELD_OPS` had to be exported for `[S09.7]` to assert it

- **Found during:** Task 3

This is **not** a fifth exception to `[S07.1]`'s banner: the `return Object.freeze({…})` sits at the end of the whole `[S07]` IIFE, after `[S07.2]`, and the comment at `:3630` explicitly describes it as taken "at that point on purpose" to describe the seams as they finally are.
- **Files modified:** `cats-vs-mechs.html`
- **Commit:** `da34c96`

### 6. [Scope boundary] `factionHead` and `unitCard` gained a `state` parameter

- **Found during:** Task 2
- **Issue:** `tallyLine` needs the current tally to seed the stepper's build-time value, and the honest read is `amountFor(state, …)`. Neither builder received `state`.
- **Resolution:** both signatures gained `state` as the first argument, and `buildColumn` — their only caller, which already holds `state` — passes it. The alternative was a second copy of the tally read inside the builder, which is precisely the "second, mechanical reason for two numbers to disagree" CLAUDE.md forbids. The line shows `App.model.bestDamage(faction)` — a derivation of the actions a student allocated, not a tally of the `dmg` type — so the word arguably names the projection rather than the type. This is a judgement call, not an oversight; recorded here so 02.1-04 or 02.1-05 can rule on it deliberately. Cost of changing it later: one extra argument at one call site.
- **Files modified:** none
