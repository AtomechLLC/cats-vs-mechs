same of the new tally steppers, which inherit the ramp rather than re-implementing it.

## Finding F-02.1-A — raised before the rehearsal, not repaired

A student-made type's stat line is built on every card the moment the type exists; `sync()` sets
`line.hidden = (amount === 0)` and `[C03]` gives that line `display:none`. The stepper — minus, field
and plus — is built **inside** that line. So at a tally of zero, every control that could raise it is
inside the thing being hidden.

Measured against the shipped harness's own stub page, immediately after "New type on each unit":

| Controls naming the new type | Present | Reachable (no hidden ancestor) |
|---|---|---|
| `nudgeTally` buttons | 24 | **0** |
| tally fields | 12 | **0** |

The same hide pass covers a side-scope type's two faction lines, so both scopes are affected.

Every automated check is honest — gate check 32 raises the first tally by calling
`App.ops.nudgeTally` directly, which is a fair way to test the render and is not a path a student
has. The consequence is that **ROADMAP § Phase 2.1 criterion 3 — "it carries a per-unit or
per-faction tally the student increments by hand" — is not reachable through the shipped UI**, and
check 8's "tally it on two cats by hand" cannot be completed without the console.

**Why nothing was changed.** This is the phase's own `<specifics>` rule working exactly as written
("a custom type with a zero tally everywhere should render as nothing on the board"), so a repair is
a design decision rather than a defect fix — deviation Rule 4, the user's call. Task 1's acceptance
also states in terms that the artifact must not be modified. Three shapes are offered in the UAT
document: reveal the line while its type is selected in the picker; a quiet zero line on the card;
or a tally control in the picker itself. The first keeps the board clean at rest and costs the hide
pass one more input.

- **Found during:** Task 1, while assembling check 8's steps
- **Issue:** a tally cannot be raised from zero anywhere on the page
- **Action:** measured with a scratch copy of the harness, recorded in the UAT document as a finding
  with three options, and added to the checkpoint. No code changed.

**2. [Rule 1 — corrected a predicted outcome] check 4's emoji paste**
- **Found during:** Task 1
- **Issue:** the plan predicts a 30-emoji paste lands at 24 emoji. `maxlength="24"` counts UTF-16
  units and each of these emoji is two, so a real paste admits about 12. Handing the human a wrong
  prediction would have produced a false failure report.
- **Fix:** the document predicts ~12, names the reason, states that the one unacceptable outcome is a
  broken half-character, and moves the 24-code-point cut into an optional console step — which is the
  path gate check 38 actually drives.
- **Files modified:** the UAT document only

**3. [Rule 1 — corrected a predicted outcome] check 7's refusal**
- **Found during:** Task 1
- **Issue:** the plan suggests forcing a refusal by removing a built-in. `Remove this type` is
  **disabled** for the five built-ins, so that message is unreachable from the UI.
- **Fix:** check 7 reads the empty-name refusal (which a student can reach) and confirms the disabled
  control separately — a bound shown rather than raised.
- **Files modified:** the UAT document only
