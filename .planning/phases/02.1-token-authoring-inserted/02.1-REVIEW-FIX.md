## Fixed Issues

### CR-01: A half-typed name commits to whichever type the editor moved to

**Files modified:** `cats-vs-mechs.html`, `tests/selftest-node.cjs`
**Commit:** `57c087e`

`commitName` now reads its target from `el.dataset.forTok`, recorded on focus-in beside
the baseline it already recorded, instead of resolving `pickedTok(dlg)` at commit time.
A pending name with no recorded type goes back rather than being guessed at.

**Departure from the review's suggested fix, deliberately.** The review also asked
`showType` to flush the pending name before moving the attribute. I implemented that,
traced it, and removed it: flushing commits the rename *before* `showType`'s own
`App.render.picker` call, so the repaint computes its fingerprint from a vocabulary that
already carries the new name. The frame that follows then sees nothing moved and never
rewrites the field the repaint had to skip while it held focus — leaving one type's
editor with another type's text in the box. Binding the text to its type fixes the
corruption without moving *when* the commit happens, so the ordinary
repaint-after-commit still puts the right name in the box. The rejected approach and the
reason are written into the `showType` comment so it is not re-attempted.

**Regression row: gate check 39.** Drives all three of the review's cases with browser
focus ordering (pointerdown handler, then the focus change). Red without the fix:

```
row press: typed-for type="New type" (want "Poison") dmg="Poison" (want "Damage")
| New: typed-for type="Poison" (want "Frost") made type="Frost" (want "New type")
| Remove: health="Venom" (want "Health")
```

Case B — Health silently renamed to Venom — needed no emulated ordering: `dropType`
calls `focus()` inside its own pointerdown handler.

### CR-02: Undoing a create leaves a ghost row and the next press raises the error panel

**Files modified:** `cats-vs-mechs.html`, `tests/selftest-node.cjs`
**Commit:** `f2d2802`

`syncPicker` now repaints onto a live type instead of returning.

**Two departures from the review's suggested fix.** It falls back to `Object.keys(vocab)[0]`
rather than exporting `FIRST_TOK` out of `[S07.2]`: this hook's own comment says it reads
its own bookkeeping and nothing else, and reaching into the interactions tier from a
render hook inverts the dependency `[S06]`'s banner declares. On the shipped board the

which is the property `onPickerClose` already relies on. There is no redo stack, so it
cannot come back to life.

output verbatim:

### WR-02: Stepping a tally to zero hides its own stepper and drops focus

**Files modified:** `cats-vs-mechs.html`, `tests/selftest-node.cjs`
**Commit:** `dda0f20`

The hide pass gains a third term: a `.brd-line--opt` the active element sits inside is
kept on screen, the same way the reveal keeps one. A line collapses on the next frame
after focus leaves it rather than under the finger.

**Judgment call, per the prompt's steer.** The alternative was to reveal the type on the
way down. I rejected it: it would make the reveal sticky for a type at zero on *every*
unit, it needs a write to state from an interaction that is currently pure, and it does
not help a student who reached zero with the pointer. The focused-line term is local,
writes nothing, and does not touch F-02.1-B — the reveal still survives the editor
closing.

**Regression row: gate check 42.** Drives the reveal *off* the type first, then steps to
zero from the keyboard with focus on the minus. Red without the term:

```

```

The check also asserts the line does collapse once focus leaves, so the fix cannot be
"never hide anything".

### WR-06: `nextTokenTypeId` re-spells `TOKEN_ID_PATTERN` inline

**Files modified:** `cats-vs-mechs.html`
**Commit:** `9a8da6b`

The width is one string, `TOKEN_ID_DIGITS`, and both readings of the id shape are built
from it: `TOKEN_ID_PATTERN` (the test) and the exported `TOKEN_ID_CAPTURE` (the same
shape with the sequence number captured). `nextTokenTypeId` scans through the exported
capturing form.

**Departure from the review's first suggestion.** It offered deriving the capture by
`.source.replace('[0-9]{1,2}', '([0-9]{1,2})')`. I rejected that: a future edit to the
pattern makes the replace silently stop matching, which yields a regex with no capture
group, `m[1] === undefined`, `Number(undefined) === NaN`, and a scanner that reads
nothing and never says so. Building both from one string cannot fail that way. This is
the review's own second suggestion.

**Proof the hazard is closed**, run against two scratch copies with the declared width
widened to three digits and `t1` and `t100` on the board:

```
BEFORE: nextTokenTypeId returns t2     <- blind to t100; contract says largest-plus-one
AFTER : nextTokenTypeId returns t101
```

Three new `[S09.7]` rows assert the two forms accept exactly the same ids across
`t1 t9 t12 t99 t100 t0 T1 hp '' t`, and that the capture hands back the number.
