## Finding raised BEFORE the rehearsal — please read first

**F-02.1-A — a tally that has never been written cannot be raised from the page.**

Measured, not inferred. A student-made type's stat line is built on every card the moment the type
exists, and `sync()` sets `line.hidden = (amount === 0)`; `[C03]` carries
`.brd-line--opt[hidden]{display:none}`. The stepper — its minus, its field and its plus — is built
*inside* that line. So at a tally of zero the only controls that could raise it are the ones being
hidden.

Instrumented against the shipped harness's own stub page, immediately after "New type on each unit":

| Controls naming the new type | Present | Reachable (no hidden ancestor) |
|---|---|---|
| `nudgeTally` buttons (12 cards x 2) | 24 | **0** |
| tally fields (12 cards) | 12 | **0** |

The same hide pass covers a side-scope type's two faction lines, so both scopes are affected.

**What this means for the rehearsal:** every automated check is honest — the gate raises the first
tally by calling the op directly, which is a legitimate way to test the render but is not a path a
student has. Check 8's "tally it on two cats **by hand**" therefore cannot be completed as written
without the console. ROADMAP § Phase 2.1 criterion 3 — "it carries a per-unit or per-faction tally
the student increments by hand" — is not reachable through the shipped UI.

**Nothing was changed to fix this.** It is a design question, not a defect with one obvious repair:
the phase's `<specifics>` deliberately say "a custom type with a zero tally everywhere should render
as nothing on the board, not as a row of empty slots", and that is exactly the rule producing this.
Any repair edits the hide pass, `[C03]`, gate check 32 and possibly the picker, so it wants your
direction rather than the executor's guess. Three shapes it could take, for discussion:

- **(a) Reveal while the type is being edited.** A zero line stays hidden except while the picker has
  that type selected — the board is clean at rest and the student who just invented a type can find
  its first number. Costs one more input to the hide pass.
- **(b) A quiet zero on the card, hidden only once used and returned to zero.** Simple to read, but
  it puts up to 12 faint lines on the board the moment a type is made, which is the clutter the rule
  exists to prevent.
- **(c) Raise the first number in the picker.** One tally control in the editor, per selected type,
  targeting a unit or the side. Keeps the board rule exactly as it is, and does not reintroduce a
  board-side edit control (D-08).

Please answer this alongside check 8 rather than instead of it.

### Check 2 — a zero tally collapses its line, and takes no space

The `[hidden]` cascade has no layout engine in the Node gate. Gate check 32 asserts the `.hidden`
property, which is the artifact's decision; whether the line then occupies no space is a question
only a browser answers. It fails OPEN — as clutter, not as a crash — which is why no assertion
catches it.

**Steps**
1. Press **Tokens**, then **New type on each unit**. The editor lands on the new type, named
   "New type". Press **Done**.

   `document.querySelector('.brd-line--opt').dataset.amt` — which is `t1` on a fresh board (ids are
   generated as `t1`, `t2`, … and never shown to the student). Then raise one number:
   `App.ops.nudgeTally('cats', 'c1', 't1', 1)`.

**Expected:** after step 2, **nothing at all** for the new type on any card — no label, no empty box,
no stepper, and no gap where a line would be. Card heights unchanged from before the type existed.
After step 4, exactly one line appears, on Cat 1 only, reading "New type" with a stepper and one
token — and no other card moves.

**Failure looks like:** 12 empty labelled boxes, or a visible gap on every card.

### Check 4 — `maxlength` on a real input

`maxlength` counts UTF-16 code units; the op's cap counts **code points**. They legitimately disagree
for an emoji name, and that disagreement only exists on a real input.

**Steps**
1. Press **Tokens**, select any type, click into the **Name** field, select all and type
   `abcdefghijklmnopqrstuvwxyz0123` (30 plain characters).
2. Count what the field holds.
3. Select all again and paste 30 skull emoji:
   `💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀💀`
4. Press **Enter**.

**Expected:**
- Step 2: the field stops at **24** characters. It refuses the 25th rather than accepting it and
  telling the student off afterwards.
- Step 3: each of these emoji is **two** UTF-16 units, so `maxlength="24"` admits at most **12** of
  them — expect about 12, and possibly 11 if the browser declines to cut through the middle of a
  pair. **The one thing that must not happen is a broken half-character on screen.**
- Step 4: the name commits, the board label matches the field exactly, and **no error panel appears**.

**Optional, with the console** — this is the path the gate drives, and it bypasses `maxlength`:
set the field's value to 30 emoji programmatically, dispatch an `input` event, then press Enter. The
name that lands must be exactly 24 emoji, whole, with no error panel.
