Render the reference material where a student needs it: the actions and their effect cards inside
each faction's own column, and what-beats-what in a full-width band below both.

D-12 amends Phase 2's D-02 deliberately. REF-02 requires effect cards attached *to the actions that
carry them*, and actions belong to a faction — they cannot be simultaneously in a shared band and
attached to a per-faction action. The three relationships are genuinely cross-faction (one of them is
even intra-Mechs), so the band is right for those and wrong for the cards.

`buildColumn`'s setup-only branch, they survive into fight mode for free and Phase 5's REF-03 is
pre-satisfied rather than re-planned.

<layout>
**Action + effect cards** — appended by `buildColumn` into each faction column, below the roster and
below the setup-only Add button. One card per action, built from `DEFAULTS[side].actions`:
the action's name, its damage, and one effect card per entry in its `keywords` array.

An action with `dmg: 0` carries no damage figure it would be misleading to print as a zero — decide
one presentation and apply it to all three zero-damage actions (Hairball, Screech, Fly, Recharge),
and say in the comment which you chose and why. `Slash` is 1 and `Lasers` is 3.

**The band** — a new static shell node inside `#board`, placed before `#board-empty`:
`<section class="brd-band" id="refband"></section>`, styled `grid-column:1 / -1`. `#board-empty`
already sets that precedent at `[C03]` L141. `structure()` replaces only the two column interiors, so
the band survives a rebuild exactly the way `#strip` does — same build-once, same
`dataset.built` flag.

**Contents are static.** They come from `App.data.REFERENCE` and `App.data.DEFAULTS`, not from
`state.build`, so the band has nothing to re-sync. Register the hook anyway, in `[S06.2]`'s shape,
and let it return early once built — that keeps every page region this file owns reconciled by the
same frame, which is the reason `SYNC_HOOKS` exists.

**Typography.** `[C04]`'s floor is the projector legibility spec, not taste: every value at least
24px and weight 700, every label at least 18px, and nothing at or below 14px may carry information.
**`.eyebrow` and `.ex` are both 12px and may not be used for reference content.** Reuse `.card`,
`.callout`, `.muted`, `.num`, `.brd-label` / `.brd-value` sizing.

**Colour.** Faction tint on a column's cards only if it matches that column's existing treatment.
The band is cross-faction and takes neutral surface colour. No colour anywhere encodes quality
(D-15), and the band's three lines must not be coloured by who wins — that is a verdict wearing a
palette.

**No inline SVG, anywhere.** `createElementNS` needs the SVG namespace URI, and `https?://` is in the
harness's `FORBIDDEN` list. If a card wants a shape, draw it in CSS with `clip-path: polygon()`, which
is what `[C05]` already does for the board's triangles and hexagons.
</layout>

<the_keyword_rename_trap>
The keyword id `shield` collides by name with the token id `shield`. **`App.render.labelFor` must
never be called for a keyword card.** A student renaming the Shield *token* to "Barrier" has not
renamed the Recharge *keyword*, and a card that followed the rename would be reporting a rule that
changed when nothing about the rule changed.

The effect card's name comes from `REFERENCE.effects[].name`. The action's name comes from
`DEFAULTS[side].actions[].name`. Neither is a token type.

The contrast case, for the reviewer who will wonder: the board's *token rows* are the opposite — they
must route through `labelFor`, and the Damage bug (`e7f14ef`) was exactly a literal used where
`labelFor` belonged. Both rules are correct; they apply to different things. Write that distinction
into the comment where the card is built, or it will be "fixed" later.

Look each keyword up with `Array.find` over `REFERENCE.effects`, never a bare index — from Phase 4 a
keyword id can arrive from a pasted build code, and a bare lookup for `'constructor'` resolves on the
prototype instead of failing.
</the_keyword_rename_trap>
